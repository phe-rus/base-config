# CLAUDE.md: `packages/config/src/collections`

Loads when working under `packages/config/src/collections/`: the three config factories, page-content blocks, and the composite field components (relationships, nav menus, links, meta, related-posts) that back them. See `packages/config/CLAUDE.md` for this package's other conventions, and `../fields/CLAUDE.md` for the plain field-type vocabulary these composites extend.

#### Three admin namespaces: `RenderView`, `ContextView`, `ProviderView`

All three live under `../admin/views/`. `RenderView` and `ContextView` are a plain function component with named sub-parts hung off it as properties (`export const X: XComponent = (...) => ...; X.Sub = (...) => ...`, typed via an intersection cast); `ContextView`/`ProviderView` are plainer, a bare object of named component references, since nothing ever renders `<ContextView>`/`<ProviderView>` directly, only their members:

- **`RenderView`** (`admin/views/render-view.tsx`) is markup-level reuse: the page-container chrome every top-level admin view shares. `RenderView` itself is the outer `<article className='container flex flex-col w-full md:max-w-4xl mx-auto gap-5 py-5'>`; `.Header`, `.NotFound`, `.List` (a titled grid of link cards), `.Breadcrumb`, `.FolderCard`/`.FileCard` (Storage's grid rows) are the named sub-parts.
- **`ContextView`** (`admin/views/dispatch/context-view.tsx`) is route-dispatch-level grouping: `{Dashboard, Entry, Storage}`. **`ContextView.X` must never be written directly as a route's `component:`**, every consumer route destructures to a local const first (`const { Entry } = ContextView` then `component: Entry`).
- **`ProviderView`** (`admin/views/dispatch/provider.tsx`) is `{Context}`, one member, `ProviderView.Context`, the component a consumer wraps the `$collection` layout route's `Outlet` in. It resolves `RouteViewState` once per navigation and provides it via `useRouteView()`. Unlike `ContextView` members, `<ProviderView.Context>` is used as plain JSX inside a route file's own component body, not as a route's `component:` value.

#### The three factories (`define.ts`)

- **`defineCollection({slug, label?, color?, path?, auth?, columns?, filterKey?, admin?, tabs})`** → a full `CollectionConfig` (`schema`, `defaultValues`, `Fields` all derived automatically from `tabs`). `label` is optional (derived via `labelFromSlug(slug)` if omitted). `path` sets the collection's public URL prefix. `auth: true` marks the real, server-backed `users` collection, every other collection is real D1-backed content (see `../db/CLAUDE.md`). `columns`/`filterKey` control `CollectionTable`'s columns. `admin.useAsTitle` names a real field to display as a document's "title" for collections without one (`users` uses `name`).
- **`defineGlobal({slug, label?, fields})`** → a full `GlobalConfig`, same derivation, minus tabs. **Or** `defineGlobal({slug, label?, component})` → a `custom: true` global whose `Fields` is `component` directly, with no schema/document/`GlobalForm` wrapper, `admin/views/dispatch/provider.tsx`'s `resolveRouteView` checks the generic `config.custom` flag and resolves it to `mode: 'custom'`, which `ContextView.Entry` renders as the whole page. For a global that isn't really a document to edit, e.g. Storage.
- **`baseConfig({queryClient, auth?, config, collections, globals, ...})`** → identity function with several side effects: registers every `collections`/`globals` entry with `collections/registry.ts`; registers `queryClient`/`contentClient`/`storageClient` unconditionally via `registerContentDataSource()`/`registerStorageDataSource()` (every consumer needs real content persistence, not just `auth`-enabled ones); if `auth` is passed, calls `registerUsersDataSource({queryClient, authClient: auth})`. Returns the same config either way.

#### Relationships (`collections/fields/Relationship/index.tsx`)

A selected relationship stores `{id, slug, title}` (`RelationshipValue`), not a bare id. The picker itself queries **every real collection via a fixed number of `useLiveQuery` calls** (`pages`/`posts`/`policies`, one each), adding a fourth collection means adding one more explicit `useLiveQuery` line in `useRelationshipOptions`. `hasMany` switches between `RelationshipFieldSingle` (plain combobox) and `RelationshipFieldMulti` (chips).

#### Nav menus and the shared link fields (`menu`/`links` field types, `collections/fields/NavMenu/index.tsx`, `collections/fields/Links/index.tsx`)

`Links/index.tsx` is the shared foundation both nav menus and content blocks build on:

- **`LinkModeFields({form, name})`**: a link's own mode/target/open-in-new-tab: `mode: 'internal'` (a `RelationshipField` reference, picking one auto-syncs `to` via `collectionPath(collectionsBySlug[value.collection], value.slug)`) or `mode: 'custom'` (hand-typed `to`), plus `openInNewTab`. Deliberately excludes `label`/`appearance`, those are a *caller's* own per-item fields (see `LinksField` below and `NavMenuField`'s own `NavItemFields`), not part of a link's mode/target itself.
- **`LinksField({form, name, label?, description?})`**: wraps `LinkModeFields` in an `ArrayField`: each item gets its own `label` plus button `appearance` (the real shadcn `Button` variants, `appearanceValues`) alongside the mode/target fields. This is `type: 'links'`'s (`../fields/types.ts`'s `LinksFieldConfig`) real implementation, and is also imported *directly* by the `cta`/`banner` blocks (`collections/blocks/Cta/index.tsx`, `collections/blocks/Banner/index.tsx`) rather than going through the generic per-field-type dispatch, the same "a block reuses a composite field component directly" pattern `relatedPosts` already uses for `RelationGroupFields`. No mega-menu option, that's `NavMenuField`'s own extra complexity, deliberately not part of this plainer, array-only field. `ArrayField`'s own default row label already works here for free, since every item has a real `label`.

`NavMenu/index.tsx` (`menu` field type) is used by both `footer` and `topbar`. Every item is a **link by default**, `NavItemFields` renders its own `label`/`appearance`/`openInNewTab`, then delegates the mode/target part to `LinkModeFields` above (`NavLinkModeFields`'s non-disabled branch calls it directly, rather than duplicating the reference/custom-URL logic a second time). Checking **"Mega menu"** drops the link fields and shows a **"Category"** toggle instead. There is no public-facing render of any of this yet, this is authoring-side only.

#### Page-content blocks (`collections/blocks/`)

Each built-in block lives in its own folder, `collections/blocks/<Name>/index.tsx` (Payload-parity, matching `packages/ui/src/forms/fields`'s own folder-per-field convention, see `../../../ui/src/forms/CLAUDE.md`): `Banner`, `Code`, `Cta`, `Grid`, `Media`, `RichText`, `RelatedPosts`. Shared infrastructure used by every block (`BlockData`, `BlockRenderer`, `BlockConfig`, `BlockFieldsProps`, `BlockSlug`) lives in `collections/blocks/shared/`, not in any one block's own folder. `registry.ts` and the public barrel `index.ts` stay at the `blocks/` root, mirroring how `packages/ui/src/forms/fields/index.ts` sits alongside its own per-field folders.

**`blocksBySlug` (`registry.ts`) is a live, runtime `Record<string, BlockConfig>`, not a closed union**, mirrors `collections/registry.ts`'s own `collectionsBySlug`/`globalsBySlug` pattern, for the same reason: a plugin package (e.g. `@baseconfig/plugin-form-builder`) can't add a member to a union type it doesn't own, so this needs to be something it can register *into* via `registerBlocks(blocks)` (called once by `baseConfig()` with `config.blocks ?? []`). Seeded eagerly with this package's own 7 built-in blocks (unlike `collectionsBySlug`, these aren't optional, a consumer gets them for free with zero registration): `richtext`, `media`, `cta`, `banner`, `grid`, `code`, `relatedPosts`. A slug collision silently overwrites the built-in (last write wins, no error), the same collision behavior `collectionsBySlug`/`globalsBySlug` already have.

- **`columns` was removed, its role fully absorbed by `grid`**, a fixed 2-column layout was just a narrower special case of what `grid` already needed to be (a general "compose blocks visually" primitive, not two overlapping ones). `grid`'s own schema validates its nested `items` loosely (`z.object({blockType: z.string()}).loose()`, to avoid a circular schema reference back to the full block union) and its `Render` recursively dispatches each item through `blocksBySlug[item.blockType]`'s own `Render`, wrapped in a `variant`-controlled layout (`default`/`card`/`bordered`, cosmetic only, no effect on the admin editor's own plain list view).
- **`media` dropped `alt`/`caption` entirely**, the real upload value's own `name`/`url`/`size` already covers what those stood in for; this block is just an image (`{blockType: 'media', image: uploadValueSchema.optional()}`).
- **`cta`/`banner` both use `LinksField`** (see above) instead of a single `buttonLabel`/`link`/`variant` triplet, `links: linksSchema.optional()`, rendered publicly as one `<a className={buttonVariants({variant: link.appearance})}>` per item.
- **`code`**: a real CodeMirror 6 editor (`@baseconfig/ui`'s `CodeEditor`/`Code` field, see `../../../ui/src/forms/CLAUDE.md`), not a plain textarea. `language`/`code` are sibling fields, but the language select itself lives inline in the editor's own top-right corner (`f.Code`'s `languages`/`onLanguageChange` props) rather than as a separate visible field, the nested-`form.AppField` pattern (`NavMenu/index.tsx`'s own `language` field's render callback wraps the `code` field's own) is the same one that lets one field's rendering react to a sibling's *current* value. A modest `looksLikeJson()` heuristic (parses on every keystroke) auto-switches `language` to `'json'` when the pasted/typed content looks like it, deliberately not real language detection, just the one case that's realistically detectable without a parser or a new dependency. `Render` builds a one-node tiptap doc (`{type: 'codeBlock', attrs: {language}, content: [...]}`) and renders it through `@baseconfig/ui/basiccn/preview`'s `Preview`, reusing the editor's own existing `CodeBlockLowlight` syntax highlighting rather than a second highlighting path. `lowlight`'s `common` bundle only registers `typescript`/`javascript`/`json` by name (no separate `tsx`/`jsx` grammar), so both map onto their non-JSX sibling for highlighting purposes, still real, readable highlighting, just not JSX-attribute-aware.
- The **`JSON` field** (`@baseconfig/ui/forms`) shares the same `CodeEditor` as `Code` but commits *parsed* JSON rather than a string, see `../../../ui/src/forms/CLAUDE.md` for the real distinction, and `../fields/CLAUDE.md` for this package's own `json` `FieldConfig` entry.

#### The circular-import trap

`collections/registry.ts` is a passive store that must never import a consumer's own `base.config.ts`, doing so creates a real, hard-crashing import cycle at runtime under a native ESM loader. See `../db/CLAUDE.md`'s "The circular-import trap" for the full cycle and the related server-side ordering bug it also documents, both center on this same registry.
