# CLAUDE.md: `packages/config/src/collections`

Loads when working under `packages/config/src/collections/`: the three config factories, page-content blocks, and the composite field components (relationships, nav menus, links, meta, related-posts) that back them. See `packages/config/CLAUDE.md` for this package's other conventions, and `../fields/CLAUDE.md` for the plain field-type vocabulary these composites extend.

#### Three admin namespaces: `RenderView`, `ContextView`, `ProviderView`

All three live under `../admin/views/`. `RenderView` and `ContextView` are a plain function component with named sub-parts hung off it as properties (`export const X: XComponent = (...) => ...; X.Sub = (...) => ...`, typed via an intersection cast); `ContextView`/`ProviderView` are plainer, a bare object of named component references, since nothing ever renders `<ContextView>`/`<ProviderView>` directly, only their members:

- **`RenderView`** (`admin/views/render-view.tsx`) is markup-level reuse: the page-container chrome every top-level admin view shares. `RenderView` itself is the outer `<article className='container flex flex-col w-full md:max-w-4xl mx-auto gap-5 py-5'>`; `.Header`, `.NotFound`, `.List` (a titled grid of link cards), `.Breadcrumb`, `.FolderCard`/`.FileCard` (Storage's grid rows) are the named sub-parts.
- **`ContextView`** (`admin/views/dispatch/context-view.tsx`) is route-dispatch-level grouping: `{Dashboard, Entry, Storage}`. **`ContextView.X` must never be written directly as a route's `component:`**, every consumer route destructures to a local const first (`const { Entry } = ContextView` then `component: Entry`).
- **`ProviderView`** (`admin/views/dispatch/provider.tsx`) is `{Context}`, one member, `ProviderView.Context`, the component a consumer wraps the `$collection` layout route's `Outlet` in. It resolves `RouteViewState` once per navigation and provides it via `useRouteView()`. Unlike `ContextView` members, `<ProviderView.Context>` is used as plain JSX inside a route file's own component body, not as a route's `component:` value.

#### The three factories (`define.ts`)

- **`defineCollection({slug, label?, color?, path?, auth?, columns?, filterKey?, admin?, access?, tabs})`** → a full `CollectionConfig` (`schema`, `defaultValues`, `Fields` all derived automatically from `tabs`). `label` is optional (derived via `labelFromSlug(slug)` if omitted). `path` sets the collection's public URL prefix. `auth: true` marks the real, server-backed `users` collection, every other collection is real D1-backed content (see `../db/CLAUDE.md`). `columns`/`filterKey` control `CollectionTable`'s columns. `admin.useAsTitle` names a real field to display as a document's "title" for collections without one (`users` uses `name`). `access` (`create`/`read`/`update`/`delete`, each optional, unset means open) is this collection's own per-operation access control, see `../api/CLAUDE.md`'s "Access control" section for the full mechanism; has no effect on an `auth: true` collection (never routed through `content-route.ts` at all, better-auth owns it entirely).
- **`defineGlobal({slug, label?, fields, access?})`** → a full `GlobalConfig`, same derivation, minus tabs. `access` (`read`/`update`, no `create`/`delete`, a global always has exactly one row) works the same way `defineCollection`'s does. **Or** `defineGlobal({slug, label?, component})` → a `custom: true` global whose `Fields` is `component` directly, with no schema/document/`GlobalForm` wrapper (no `access` either, same reasoning, there's no `content-route.ts` endpoint for it to gate), `admin/views/dispatch/provider.tsx`'s `resolveRouteView` checks the generic `config.custom` flag and resolves it to `mode: 'custom'`, which `ContextView.Entry` renders as the whole page. For a global that isn't really a document to edit, e.g. Storage.
- **`baseConfig({queryClient, auth?, config, collections, globals, ...})`** → identity function with several side effects: registers every `collections`/`globals` entry with `collections/registry.ts`; registers `queryClient`/`contentClient`/`storageClient` unconditionally via `registerContentDataSource()`/`registerStorageDataSource()` (every consumer needs real content persistence, not just `auth`-enabled ones); if `auth` is passed, calls `registerUsersDataSource({queryClient, authClient: auth})`. Returns the same config either way.

#### Relationships (`collections/fields/Relationship/index.tsx`)

A selected relationship stores `{id, slug, title}` (`RelationshipValue`), not a bare id. `useRelationshipOptions` reads real, registered collections from `collectionsBySlug` (`../registry.ts`), not a hardcoded slug list: `targetType` (the `RelationshipField` prop; `RelationshipFieldConfig`/`MenuFieldConfig`/`LinksFieldConfig`'s own `relationTo` at the field-config level) narrows to one or more specific collections, omitting it searches every collection this app has registered, minus `users` (real accounts aren't a relatable content type, see `../db/CLAUDE.md`). React's rules of hooks still forbid looping `useLiveQuery` over a runtime-length list, so the hook queries through a **fixed number of `useLiveQuery` "slots"** (`MAX_RELATIONSHIP_TARGETS`, currently 8) instead, each slot subscribing to whichever real slug `targets[i]` currently names, or a shared, always-empty stand-in once `targets` runs out or a named slug isn't registered in this app (`getContentCollection`, `../../db/collections.ts`, resolves an unregistered slug to that same empty stand-in rather than throwing). Raising the cap means adding one more explicit slot line. `hasMany` switches between `RelationshipFieldSingle` (plain combobox) and `RelationshipFieldMulti` (chips).

#### Nav menus and the shared link fields (`menu`/`links` field types, `collections/fields/NavMenu/index.tsx`, `collections/fields/Links/index.tsx`)

`Links/index.tsx` is the shared foundation both nav menus and content blocks build on:

- **`LinkModeFields({form, name, relationTo?})`**: a link's own mode/target/open-in-new-tab: `mode: 'internal'` (a `RelationshipField` reference, `relationTo` forwarded straight to its `targetType`, picking one auto-syncs `to` via `collectionPath(collectionsBySlug[value.collection], value.slug)`) or `mode: 'custom'` (hand-typed `to`), plus `openInNewTab`. Deliberately excludes `label`/`appearance`, those are a *caller's* own per-item fields (see `LinksField` below and `NavMenuField`'s own `NavItemFields`), not part of a link's mode/target itself.
- **`LinksField({form, name, label?, description?, relationTo?})`**: wraps `LinkModeFields` in an `ArrayField`: each item gets its own `label` plus button `appearance` (the real shadcn `Button` variants, `appearanceValues`) alongside the mode/target fields. This is `type: 'links'`'s (`../fields/types.ts`'s `LinksFieldConfig`) real implementation; a consumer's `links`-typed fields (e.g. `cta`/`banner` blocks) get it for free through the generic per-field-type dispatch, and a genuinely custom block editor can import it *directly* (the same "a block reuses a composite field component directly" pattern `relatedPosts` already uses for `RelationGroupFields`). No mega-menu option, that's `NavMenuField`'s own extra complexity, deliberately not part of this plainer, array-only field. `ArrayField`'s own default row label already works here for free, since every item has a real `label`.

`NavMenu/index.tsx` (`menu` field type) is used by both `footer` and `topbar`. Every item is a **link by default**, `NavItemFields` renders its own `label`/`appearance`/`openInNewTab`, then delegates the mode/target part to `LinkModeFields` above (`NavLinkModeFields`'s non-disabled branch calls it directly, rather than duplicating the reference/custom-URL logic a second time). Checking **"Mega menu"** drops the link fields and shows a **"Category"** toggle instead. There is no public-facing render of any of this yet, this is authoring-side only. `MenuFieldConfig`'s own optional `relationTo` threads down through every level (`NavItemFields` → `NavLinkModeFields`/`MegaMenuFields` → `NavMenuLinkFields` → `LinkModeFields`) to restrict every item's "Reference" picker the same way `LinksField`'s does; a consumer with e.g. only a `pages` collection (no `posts`/`policies`) should still pass `relationTo: ['pages']` on `menu`/`links` fields it wants restricted, but omitting it is always safe too, since the picker now degrades to real registered collections rather than a fixed guess.

#### Page-content blocks (`collections/blocks/`)

**This package ships no built-in blocks.** `collections/blocks/` is pure machinery; every block a consumer can pick in the admin comes from the consumer's own `config.blocks` (Payload-style, the block tree lives consumer-side: see `www/src/config/blocks`, which is the in-repo reference for the shape). The machinery: `shared/` (`BlockConfig`, `BlockFieldsProps`, plus the `defineBlock` factory and its `BlockDefinition` input), `registry.ts` (`blocksBySlug`, `registerBlocks`, `getBlocksSchema`), and the public barrel `index.ts`.

**The consumer owns the block tree, two files per block by default, Payload's `templates/website` layout.** Each block is a folder `www/src/config/blocks/<Name>/` holding a `config.ts` (the `defineBlock` call, the library's job) and a `Component.tsx` (www's own public markup); the admin-authoring half needs **no consumer file at all**, `defineBlock` derives each block's `Fields` from its `fields` (see the `deriveBlockFields` bullet below). Only a block with a genuinely custom editor keeps a third `Fields.tsx`. A top-level `RenderBlocks.tsx` mirrors Payload's `blockComponents` record (one entry per slug) plus a `hasBlocks` guard, so public rendering is entirely consumer-owned and nothing in the library ever dispatches a block. A consumer adds a block by adding one folder and one entry in its own `blockComponents` record and `blocks` array; no library change is involved.

**Every block is authored through `defineBlock({slug, label?, fields, Fields?, Render?, Icon?, interfaceName?, group?, disableBlockName?})`** (`shared/define-block.tsx`), the block counterpart to `defineCollection`/`defineGlobal` (same optional-`label` rule, derived from `slug` via `labelFromSlug()` when omitted): `fields` (the same `FieldConfig[]` shape `defineGlobal` takes) derives `schema` via `fieldsToSchema` with `blockType: z.literal(slug)` **and `blockName: z.string().optional()` auto-injected** (Payload's per-instance block name, an author never writes either discriminant by hand) and `defaultValue` via `deriveDefaultValues` and **`Fields` via `deriveBlockFields` when omitted** (a `defaultValue`/`schema` override is available for the cases plain fields can't express, e.g. a plugin's strict reference validation; an override must *not* include `blockType`). `group` sorts the block under a heading in `BlocksField`'s "Pick block" dialog, `disableBlockName` hides that block's per-instance "Block name" input (the schema still accepts a `blockName`, the flag only controls the editor). `fields` is also what `base gen`'s type generator walks (`../db/content-types-schema.ts`) to emit each block's own **named, top-level interface** in a consumer's generated `base.types.ts`, auto-named as a PascalCase form of the slug (`'relatedPosts'` -> `RelatedPosts`), `interfaceName` (`interfaceName?` in the `defineBlock` call above) is an override of that auto-derivation, all Payload's exact rules: every block always gets a top-level interface and all are combined into the generated `ContentBlock` union (each interface carrying the same optional `blockName?: string`); two blocks that collide on an *auto-derived* name keep the first clean and suffix the later one with a short content hash, while explicit `interfaceName`s are used verbatim.. It lives in `shared/` rather than `define.ts` because it's imported by the block files themselves: `define.ts` sits *above* the blocks subtree (it imports `BlocksField`/`getBlocksSchema`), so a block importing `define.ts` would create a real TDZ cycle at module-eval time; `shared/define-block.tsx` sits *inside* it and only imports `fields/schema.ts`/`collections/types.ts` (neither depends on blocks) plus `getBlocksSchema` from `registry.ts`, which is safe for the same reason a block's own `Fields` reading `blocksBySlug` is (lazy call-time reference, never a module-scope one). `BlocksField` (`fields/BlocksField/index.tsx`) is where the Payload-parity admin features live: the per-instance block name, the `group` headings, and the `minRows`/`maxRows` count enforcement (`BlocksFieldConfig`, schema-side `superRefine` on the lazy block array plus a live count and a disabled "Add block" button at `maxRows`). Each block's collapsed row (rendered through `ArrayField`'s `renderItemHeader`, so it keeps the shared drag handle + three-dots row menu) shows a zero-padded index, the block's slug, and the block name edited **in place** as a transparent, headline-styled `input` bound to `blockName` (the same invisible chrome as a document's title input in `collection-form.tsx`, deliberately not the generic `f.Input` chrome, with `stopPropagation` so focusing it never toggles the collapsible), the block's own `label` beneath it; a `disableBlockName` block shows index + slug + label with no input. The "Add <field label>" button lives **below the block stack** (`ArrayField`'s `addAtBottom`), not above it, and its text always takes the field's `label` (`Add {label ?? name}`). A `blocks` field also carries Payload's `blocks` restriction list (`BlocksFieldConfig['blocks']`, `../fields/types.ts`): `blocks: ['cta', 'banner']` narrows the picker *and* the schema (`getBlocksSchema(slugs)`, `registry.ts`, an unregistered slug throws) *and* the generated types (the field emits `(CtaBlock | BannerBlock)[]` instead of `ContentBlock[]`), while omitting it stays "every registered block". The list autocompletes against the consumer's own generated `GeneratedBlockSlug` (`../base.types.ts`), typed through `CollectionDefinition['tabs']`/`GlobalDefinition['fields']`/`BlockDefinition['fields']`'s second generic.

**A block's admin `Fields` is derived from its `fields` by default, so a standard block's `fields` array is its entire authoring surface** (`deriveBlockFields` in `shared/define-block.tsx` renders each field through the exact same generic `renderField` dispatch collections/globals use, prefixed by the block instance's own `path`). Storage subfolders a hand-written editor used to hardcode are now field-level: an `upload` field's `prefix` yields `[uploadFolder, id, field.prefix].filter(Boolean).join('/')` (see `cta`/`banner`-style blocks declaring `prefix: 'banner'`), and a `blocks` field's `exclude` replaces a hand-written `BlocksField exclude={[...]}` (a `grid`-style block declares `exclude: ['grid']` on its own `items` field to keep from nesting itself). **Only a genuinely custom editor supplies `Fields`**, and it composes the library's exported composite field components (from `@baseconfig/core`'s barrel, the block-authoring surface): `LinksField` (a repeatable button list), `RelationGroupFields` (a `relatedPosts`-style single relation group), `BlocksField` (nested blocks), and `uploadFile`/`StorageWidget` (an `upload`-typed block's real storage round-trip, see `fields/renderer.tsx`'s generic `case 'upload'` for the wiring pattern). A block whose editor reacts to a sibling field's live value (e.g. a `code` block's corner language toggle) uses the same nested-`form.AppField` pattern the composite fields themselves use.

**`blocksBySlug` (`registry.ts`) is a live, runtime `Record<string, BlockConfig>`, not a closed union**, mirrors `collections/registry.ts`'s own `collectionsBySlug`/`globalsBySlug` pattern, for the same reason: a plugin package (e.g. `@baseconfig/plugin-form-builder`) can't add a member to a union type it doesn't own, so this needs to be something it can register *into* via `registerBlocks(blocks)` (called once by `baseConfig()` with `config.blocks ?? []`). It **starts empty, exactly like `collectionsBySlug`**: with no built-in blocks there's nothing to seed, a consumer gets zero blocks until it registers its own. A slug collision silently overwrites (last write wins, no error), the same collision behavior `collectionsBySlug`/`globalsBySlug` already have. `getBlocksSchema()` also lives here (it reads `blocksBySlug`), not in the barrel `index.ts`, so `shared/define-block.tsx` can import it without pulling the barrel back in; the barrel re-exports it. An empty registry resolves to `z.array(z.never())` (only the empty array is valid, any block instance rejected) since `z.discriminatedUnion` with zero options would throw.

#### The circular-import trap

`collections/registry.ts` is a passive store that must never import a consumer's own `base.config.ts`, doing so creates a real, hard-crashing import cycle at runtime under a native ESM loader. See `../db/CLAUDE.md`'s "The circular-import trap" for the full cycle and the related server-side ordering bug it also documents, both center on this same registry.
