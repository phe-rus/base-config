# CLAUDE.md: `packages/config/src/admin`

Loads when working under `packages/config/src/admin/`: SSR safety, the admin session guard, the auth screens, and the storage admin page. See `packages/config/CLAUDE.md` for this package's other conventions, and `../collections/CLAUDE.md` for the `RenderView`/`ContextView`/`ProviderView` namespaces this directory implements.

#### SSR safety

`CollectionForm`/`GlobalForm` (`admin/views/document/`) gate their entire subtree behind a `mounted` state flag before rendering `config.Fields`, this is why `MetaFields`/`RelationsField`/`RelationshipField`/`NavMenuField` (all of which call `useLiveQuery`) never need their own SSR guard. Don't add a *new* top-level admin surface that renders one of these composites without going through `CollectionForm`/`GlobalForm`'s existing mount gate.

#### The admin session guard: no route files, no consumer wiring at all

**Admin auth has zero route files of its own.** `login`/`create-account`/`forgot-password`/`reset-password` are reserved `$collection` values the *already-existing* `admin/$collection/$` catch-all resolves, the exact same one-dispatcher mechanism every real collection/global already goes through (`provider.tsx`'s `resolveRouteView`/`entry.tsx`'s `Entry`, see `../collections/CLAUDE.md`'s "Three admin namespaces"), not a second routing system. This replaced an earlier, more elaborate design (a separate `(auth)` pathless route group, four thin per-screen route files, a `guard.ts`-exported `adminLoader()`/`redirectIfAuthenticated()` pair a consumer wired into `loader:`) once a real technical blocker surfaced: TanStack Router loader `context` was never actually populated with `session` anywhere in a typical consumer app (no `beforeLoad` exists at all): the loader-based guard type-checked but never received a real session at runtime. The fix was to stop trying to gate at the loader level and instead read session the same way `Topbar`'s own greeting already did: better-auth's client, not router context.

- **`useAdminSession()`** (`admin/functions/session-query.ts`) is the one shared session read every admin gate uses, `Topbar`, `ProviderView.Context`, `Dashboard`. **Not** a raw `authClient.useSession()` call per site: an earlier version of this had all three call `useSession()` independently (better-auth's own reactive client hook), which produced real, confirmed duplicate `/api/auth/get-session` traffic, each subscription re-fetched on its own. `useAdminSession()` instead wraps `createSessionQueryOptions()` (below) around `authClient.getSession()` (better-auth's *promise*-based client method, not `fetch`), so every caller shares one TanStack Query cache entry (`queryKey: ['base-config', 'session']`), real deduplication. Returns `{data, isPending, hasSession}`; `hasSession` is the one boolean every caller branches on, and it's also `true` when `baseConfig()` was never given an `auth` client at all (nothing to gate against, same as this feature not existing). No manual cache invalidation on sign-in/sign-out, both already navigate with `reloadDocument: true`, which discards the whole client-side cache anyway.
- **Session gating lives in three places, all reading the same `useAdminSession()`**: **`Topbar`** (`admin/views/topbar.tsx`) always provides `AdminConfigContext` (plain app config, not chrome, `Entry`'s own `useAdminConfig()` call is unconditional, so this has to be true even when the chrome below is suppressed), then renders `TopbarChrome` only when `hasSession`, bare `children` otherwise (so the reserved-`$collection` auth screens render unwrapped), plus a `useEffect` that redirects to `/` with a `?msg=` when a session exists but the role isn't `'admin'`, the one piece of the old loader-based guard that's still real, working gating, just moved to where a real session read is actually possible (a `loader` can't call a hook). **`provider.tsx`'s `resolveRouteView`** checks `hasSession` first: with no session, `slug` (i.e. `$collection`) resolves against the reserved auth-screen names instead of `collectionsBySlug`/`globalsBySlug`, defaulting to `'login'` for anything else; with a session, resolution is **100% unchanged** from before this feature existed. **`Dashboard`** (`admin/views/dashboard/component.tsx`) needs its own check too, `/admin` (bare index) is mounted by a *separate* route (`admin/index.tsx`) that never goes through the `$collection/$` catch-all at all, so `Topbar` hiding its own chrome doesn't stop `Dashboard` itself from still rendering underneath; `!hasSession` renders `LoginView` directly instead (no `$collection` segment exists at this bare path, so the fallback is unambiguous).
- **`entry.tsx`'s `Entry`** dispatches the four new `RouteViewState` modes (`admin/functions/context.ts`) to `LoginView`/`CreateAccountView`/`ForgotPasswordView`/`ResetPasswordView` directly, with zero props, same file, same "just render whichever mode `useRouteView()` reports" job it already had for `list`/`edit`/`global`/`custom`/`not-found`.
- **`guard.ts`'s `requireAdminSession`/`adminLoader`/`redirectIfAuthenticated` still exist**, exported from `@baseconfig/core/admin` as a general-purpose *alternative*, a consumer whose own app genuinely does populate `context.session` (a real `beforeLoad`) could still use the separate-URL-redirect model these provide.

#### `Topbar`'s sign-out mutation (`admin/views/topbar.tsx`)

`Topbar` takes no `signOut`/`onSignOut` prop at all, it calls `getAuthClient()` and builds its own `useMutation` internally (inside `TopbarChrome`, only ever rendered once a session exists), deriving the button's `disabled`/label text from `isPending`. On success it navigates to `/admin/login`, still a real, working URL (the reserved-`$collection` dispatch above resolves it), just not a distinct route file anymore.

#### Admin auth screens, fully self-contained with zero consumer props (`admin/views/auth/{auth-banner,login-view,create-account-view,forgot-password-view,reset-password-view}.tsx`)

Admin auth is entirely the library's own, there is no public-facing sign-in flow at all, and a consumer never renders any of these views directly (`entry.tsx` does, per the reserved-`$collection` dispatch above) or passes them props. Each owns its own zod schema and calls `authClient.*` (`getAuthClient()`) directly.

- **`LoginView`**: email+password only, deliberately, no username sign-in (`signIn.email` unconditionally, no merged `credentials` field). Passkey sign-in and the 2FA challenge step are **feature-detected**, not configured: `authClient.signIn.passkey`/`authClient.twoFactor` are only present when the consumer's own `authClient.ts` actually registered those client plugins (`passkeyClient()`/`twoFactorClient()`), a safe, real runtime check with no server round-trip. This is also how a consumer keeps passkey available server-side (`auth.ts`'s own `passkey()` plugin) while still not offering it in *this* admin panel: just don't register `passkeyClient()` on the `authClient` instance passed to `baseConfig({auth})`. A successful `signIn.email` call whose result carries `twoFactorRedirect: true` swaps the form for an OTP-code step (`otpForm`, `authClient.twoFactor.verifyTotp`) rather than navigating away. Social sign-in **isn't** feature-detectable the same way (social providers are configured server-side with real secrets, no "list configured providers" client endpoint exists), so `icon`/`socialProviders` both default from `getAdminConfig()` (`admin/functions/config-registry.ts`, a plain module-level registry, not React context, set once by `baseConfig({config})`; a consumer states `config.socialProviders` once, app-wide, e.g. `['github', 'google']` to match what's actually configured in `auth.ts`), both remain overridable props for a caller that wants something different, just never *required*.
- **`CreateAccountView`**: same boundary, `authClient.signUp.email` only (name/email/password, no username field, no `isUsernameAvailable` check). Same `getAdminConfig()`-defaulted `icon`/`socialProviders`.
- **`ForgotPasswordView`**: one `email` field, `authClient.requestPasswordReset({email, redirectTo: resetPasswordHref})`. Always shows the same "if that email exists…" confirmation regardless of whether the account actually exists, standard practice, never reveals account existence either way. `icon` defaults from `getAdminConfig()`.
- **`ResetPasswordView`**: the other half, reads its own `?token=` directly via `useSearch({strict: false})` (no `validateSearch` anywhere, there's no route file left to put one on, and a full zod-validated search schema was more ceremony than one optional string warranted), calls `authClient.resetPassword({newPassword, token})`. No token in the URL renders an error state instead of a form. `icon` defaults from `getAdminConfig()`.
- All four are typed against `BetterAuthAdminClient`'s widened structural type (`../db/collections.ts`), confirmed correct by real `tsc` errors against the actual `authClient` instance, not guessed: `authClient.requestPasswordReset`, not `forgetPassword` (better-auth's actual endpoint is `/request-password-reset`, confirmed by reading `api/routes/password.mjs`).
- `AuthBanner` (icon/title/description header every screen shares) takes `icon` as a plain URL prop rather than a hardcoded favicon path.

**`createSessionQueryOptions<TSession>(getSession: () => Promise<TSession>)`** (`admin/functions/session-query.ts`) still exists, still exported, but a typical consumer's own admin flow doesn't have to call it directly, session reads there go through `getAuthClient()?.useSession()` (above), not a `createServerFn()`+`queryOptions()` pair. It remains a real, usable option for a consumer that genuinely wants a server-fn-backed session query (e.g. one whose router really does populate `context.session` via a real `beforeLoad`).

#### Storage: a real R2-backed media library

File storage is real and server-backed, `MEDIA` (the R2 binding) has application code reading and writing it via `@baseconfig/core/api/storage-route`'s `createStorageRoute(bucket)` (`GET /list`, `POST /upload`, `DELETE /file`, `DELETE /folder`, all gated by an admin-only check on `session.user.role`, see `../api/CLAUDE.md`). The client side (`../fields/storage-client.ts`) goes through a real `StorageApiClient` (Hono RPC, `createStorageApiClient`), never raw `fetch`.

- **Per-collection, per-document folder scheme.** Every collection/global gets its own folder automatically, named after its own `slug`, `createFieldsRenderer`/`createFlatFieldsRenderer` (`../fields/renderer.tsx`) take a `uploadFolder` param, threaded down to every `upload` field's `renderField` call. Each field also gets the *document's own id* folded in, and an optional field-level `prefix` nested under that: `uploadPrefix = [uploadFolder, id, field.prefix].filter(Boolean).join('/')`.
- **The `meta` composite gets its own top-level folder**, SEO images land at `meta/<collectionSlug>/<id>/<filename>`.
- **The Storage admin page** (`admin/views/storage/component.tsx`, exporting `Storage`, dispatched via `ContextView.Storage`, mounted at `/admin/storage`) is a **real registered global** using `GlobalConfig`'s `custom` capability (`defineGlobal({slug: 'storage', component: ContextView.Storage})`, see `../collections/CLAUDE.md`). Folder-by-folder: real `Breadcrumb`/`BreadcrumbList`/etc., a grid of files, delete buttons on both (a deleted folder just deletes every R2 object under that prefix).
- **`StorageWidget`** (`admin/widgets/storage-widget.tsx`) is the `Upload` field's "choose existing, or drag-and-drop a new one" picker. Browses every file as **one flat list** (`GET /list?flat=true`).
