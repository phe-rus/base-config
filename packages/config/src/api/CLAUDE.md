# CLAUDE.md: `packages/config/src/api`

Loads when working under `packages/config/src/api/`: the Hono route factories, content CRUD, public-read caching, the CDN route, and storage. See `packages/config/CLAUDE.md` for this package's other conventions, and `../db/CLAUDE.md` for the query layer these routes call into.

#### Routing shape

`createContentRoute(db)` (`content-route.ts`) is a Hono factory, not a pre-built app, taking only `db`, no registry, no consumer-side list of valid slugs; an unrecognized collection surfaces as `UnknownTableError`, caught by the route's own `.onError()` handler and turned into a 404. Mounted at the API's own root by `createBaseConfigRoute()`, a collection's real REST address is `/api/<collection>`, a global's is `/api/globals/<slug>`, matching Payload's own REST shape. Real `@hono/zod-validator` schemas gate `POST`/`PATCH` bodies and the list route's query params. `/globals` is registered before the `/:collection` wildcard in the route's own chain, Hono resolves an ambiguous match by registration order, not static-vs-dynamic priority, confirmed empirically.

#### Access control (`content-route.ts`, `base.types.ts`)

Every operation (`create`/`read`/`update`/`delete` per collection, `read`/`update` per global) is gated by that collection/global's own `access` config (`CollectionAccess`/`GlobalAccess`, Payload's own per-collection access model: https://payloadcms.com/docs/access-control/overview), not a single blanket admin check. **Unset means open, not denied**: a collection with no `access` config at all is fully open to everyone, matching Payload's own documented default; `templates/basics`/`templates/pharmacy` state real access (`authenticated`, `authenticatedOrPublished`, their own `src/config/access/*.ts`) on every collection that needs it, the same way Payload's own generated templates always do. `read` alone can return a `WhereCondition` (`db/content-queries.ts`) instead of a plain boolean, to scope *which* documents are visible (e.g. `authenticatedOrPublished`'s `{status: {equals: 'published'}}` for an anonymous request) rather than an all-or-nothing allow/deny.

`../db/content-operations.ts`'s `resolveAccess()` is the one place every write (via that file's own `performCreate`/`performUpdate`/`performDelete`/`performPrune`/`performUpsertGlobal`/`performPruneGlobal`) and every read (called directly by `content-route.ts`'s own list/get routes) actually calls into this; the route itself stays registry-free (same reasoning `ContentRouteBindings['hooks']` already has): `access` arrives as an explicit `Record<string, CollectionAccess | GlobalAccess>` param, built by `createHandler()` merging `collectAccess()`'s Tier-1 map (`collections/registry.ts`, populated by whatever `defineCollection`/`defineGlobal({access: {...}})` a consumer registered) with its own Tier-2 override, the identical merge shape `hooks` already uses. A denied write throws `content-operations.ts`'s own `AccessDeniedError`, caught by `content-route.ts`'s `.onError()` handler (same pattern `UnknownTableError` already has) and turned into a 401.

**Caching interacts with this**: only a genuinely scoped read (`access.read` returned a `WhereCondition`, not a plain `true`) is ever cache-eligible, see the caching section below for why.

#### Local API (`local-api.ts`)

`createLocalAPI({db, hooks?})` is `ContentApiClient`'s (`../db/collections.ts`) in-process sibling: the exact same Payload-Local-API-named operations, backed directly by `../db/content-operations.ts`/`../db/content-queries.ts` instead of an HTTP `fetch` through `hc<...>()`. For server-side code (a TanStack Start server function/loader, a cron job) running in the same Worker that would otherwise round-trip to its own `/api/*` route to read its own content, confirmed the HTTP-only gap was real: `db/collections.ts`'s `createContentApiClient` always builds a real `hc<BaseConfigRouteType>()` client, even server-side in the same isolate that hosts the route it's calling. Plain awaitable functions, not TanStack Query `queryOptions()`/`mutationOptions()` like `base` (`db/content-client.ts`) returns, see that file's own doc comment for why: this is for a call site that wants a bare `await`.

**`overrideAccess` defaults to `true`** (every method takes it, alongside an optional `user`), the opposite default from `content-route.ts`'s own HTTP routes: an HTTP request is never automatically trusted, but a Local API call already originates from the consumer's own server-side code holding the D1 binding directly, matching Payload's own Local API default (https://payloadcms.com/docs/local-api/overview#accessing-local-api). Pass `overrideAccess: false` plus a real `user` to have a call honor that user's own real access, e.g. server-rendering a page exactly as that user would see it.

Same circular-import-trap constraint `createHandler()` already has (see `../db/CLAUDE.md`): call `createLocalAPI()` from the same module as `createHandler()` (after the same `import './config/base.config'` side effect), exporting both, not a second, separate server entry point.

#### Public-read caching (`content-route.ts`, `cdn-route.ts`, `storage-route.ts`)

`createContentRoute`/`createHandler`'s optional `cache` (a `KVNamespaceLike`, `env.CACHE` in a typical consumer) fronts every genuinely scoped read with a cache-aside pattern: a write invalidates the relevant key(s), the next matching read repopulates. Never consulted when `access.read` resolved to a plain `true` (sees everything, potentially drafts included): caching that response under a key with no per-session component would leak it to the next, less-privileged request hitting the same key. Three shapes:

- **A single document by `id`** (`GET /:collection/:id`, key `content:<collection>:<id>`), the original shape.
- **A single document by `slug`** (`GET /:collection?where={"slug":{"equals":"..."}}` with no other filter/pagination, key `content:<collection>:slug:<slug>`), added because a public URL resolves to a document by slug, never by id, so the id-keyed cache above is never actually reachable from a real page-by-slug lookup. `content-route.ts`'s `slugCacheKey()`/`documentCacheKey()` are colocated deliberately so the two can never drift. On `PATCH`, the document's slug is read *before* the write (`getDocument`) specifically so a rename invalidates both the old and new slug keys, not just whichever one the post-write row happens to have; `DELETE` reads it the same way, since there's nothing left to read from afterward.
- **A single global** (`GET /globals/:slug`, key `content:global:<slug>`), plus the aggregate `GET /globals` (every registered global in one response): both now go through one shared `getCachedGlobal()` helper inside `createContentRoute`, so the aggregate list benefits from the same caching the single-global route already had (it didn't, before this: `GET /globals` called `getGlobal` directly).

A plain filtered/paginated document list is still never cached, no single natural cache key the way one document does, see `ContentRouteBindings['cache']`'s own doc comment for the full reasoning.

**Media has a separate, already-real two-layer edge cache**: `cdn-route.ts`'s `/api/cdn/*` (browser `Cache-Control` plus the Workers `caches.default` API), so a warm edge location serves a repeat request without ever touching R2. `storage-route.ts`'s file/folder `DELETE` handlers call `cdn-route.ts`'s exported `purgeCdnCache(origin, key)` afterward, so a deleted file doesn't keep serving stale bytes from a warm edge location for up to its own `max-age` (1 hour), this didn't happen before either. `purgeCdnCache` mirrors `createCdnRoute`'s own cache-key construction exactly (same `/api/cdn/<key>` path assumption `storage-route.ts`'s own listing URLs already make), built from the deleting request's own origin rather than an incoming CDN request's. **Not yet handled**: re-uploading a file under an existing key (the CDN cache-key doc comment's claim that `must-revalidate` handles this is about the *browser*'s own cache, not the Workers edge cache, which has no revalidation logic in this code at all, a real, separate gap from the delete one).
