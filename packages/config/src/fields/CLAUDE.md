# CLAUDE.md: `packages/config/src/fields`

Loads when working under `packages/config/src/fields/`: the field vocabulary, schema deriver, and field renderer at the core of `@baseconfig/core`. See `packages/config/CLAUDE.md` for this package's other conventions.

#### Field types (`fields/types.ts`)

Primitives (dispatched generically to a matching `@baseconfig/ui/forms` control): `text`, `textarea`, `richtext`, `checkbox`, `switch`, `date`, `keywords`, `upload`, `select`, `combobox`, `radio`, `email`, `number`, `password`, `confirmPassword`, `hidden`, `code`, `json`, `slug`, `point`. Every leaf type `@baseconfig/ui/forms` ships is now wired into this union, `renderer.tsx`'s dispatch, and `schema.ts`'s zod mapping (`email` validates format, `number` maps to `z.number()`, `json`/`point` get their own shapes, the rest map to `z.string()`). `combobox` is `select`'s exact value shape (a single option out of a fixed list), just rendered as a searchable combobox instead of a plain dropdown, for a long enough option list that typing to filter beats scrolling; its own `emptyLabel` controls the no-match message. `text`/`textarea` carry optional `minLength`/`maxLength`; `number` carries `min`/`max`/`step`. No other type has field-level bounds validation yet. `array` recurses (its own `fields` describe one item's shape; nested array item paths compose via `${path}.${field.name}`).

`confirmPassword` mirrors `password`'s own `z.string()` schema shape for now. The actual "must match its sibling password field" rule is a whole-document concern this schema deriver doesn't check (no field-level `validate` or cross-field hook exists), same boundary `@baseconfig/ui/forms`'s `ConfirmPassword` component already documents on itself.

Composites (each dispatched directly to an app-supplied component via `define.ts`'s resolver maps, not through the generic primitive switch): `blocks` (page-content blocks, see `../collections/CLAUDE.md`; carries Payload's `minRows`/`maxRows`, enforced schema-side with a `superRefine` wrapper on the lazy block array (never `.unwrap()`, which would eagerly evaluate the `z.lazy` and break deferred registration, see `schema.ts`'s `case 'blocks'`) plus a live count and a disabled "Add block" button at `maxRows` in `BlocksField`), `relationship` (single/multi document reference, see `../collections/CLAUDE.md`), `keywords` (a *framework-owned* composite, see below), `meta` (SEO title/description/image/keywords bundle), `menu` (nav menus), `links` (a repeatable per-item label plus button appearance plus link-target list, shared with `menu`'s own per-item link fields, see `../collections/CLAUDE.md`'s nav menu section).

`BlocksFieldConfig['blocks']` (`types.ts`) is a `blocks` field's own **allow-list restriction**, Payload's `blocks` field option: `blocks: ['cta', 'banner']` narrows the "Pick block" menu (`BlocksField`), the schema (`getBlocksSchema(slugs)` via `schema.ts`'s `case 'blocks'`, an unregistered slug throws), and the generated types (the field emits the narrowed union `(CtaBlock | BannerBlock)[]` instead of `ContentBlock[]`, `../db/content-types-schema.ts`); `blocks: []` is "explicitly nothing" (`never[]`, runtime `z.array(z.never())`); omitting it stays "every registered block". The list is typed as `TBlockSlug[]` defaulting to the consumer's generated `GeneratedBlockSlug` union (falls back to a plain `string` in a plugin package), so it autocompletes against the consumer's own registered slugs.

**Layout/grouping field types** (Payload-modeled): `row`/`collapsible` (`{type, fields}`, no `name`, pure presentational grouping, fields splice flat into the parent object exactly as if the container weren't there), `group` (`{type: 'group', name?, label?, description?, fields}`, nests under `name` if given, splices flat if omitted, matching Payload's own real behavior), `tabs`-as-a-field (`{type: 'tabs', tabs: [{id, label, name?, fields}]}`, each sub-tab independently named/unnamed, same nest-or-splice rule as `group`, scoped to a single level in this pass: a sub-tab's own fields can freely use `row`/`collapsible`/`group` but not a second nested `tabs`-as-field), `ui` (`{type: 'ui', Component: FC}`, a blank, data-free admin-only slot, contributes nothing to schema/defaultValues). All five are resolved away by `schema.ts`'s `expandFields()` (idempotent, safe on both a raw field list and an already-flattened one) before any real schema/defaultValue derivation ever sees them. `isContainerFieldType()` (`fields/types.ts`) is the single source of truth both `schema.ts` and `renderer.tsx` key off, so the type list can't drift between the two files. `renderer.tsx`'s `renderField` dispatches all five as early-return branches before it computes `field.name` (which none of them have): `row` renders a flex row, `collapsible` wraps `@baseconfig/ui`'s `Collapsible`/`CollapsibleTrigger`/`CollapsibleContent`, `group` renders a `<fieldset>` with an optional `<legend>`, `tabs`-as-field renders nested `Tabs`/`TabsList`/`TabsContent` chrome per sub-tab, `ui` renders `field.Component` directly. None of the five use `form.AppField` themselves (that only ever wraps a real, named leaf field further down the recursion).

`relationship` is the one composite the renderer doesn't hand to a resolver component the usual way: it stays on `FieldRenderers` for a consumer that genuinely wants its own picker, but the *default* picker (`RelationshipField`, `../collections/fields/Relationship`) is dispatched by `renderer.tsx` itself (`renderField`'s `case 'relationship'`, forwarding `hasMany`/`minRows`/`maxRows` and the field's `admin.description`), so an ordinary consumer config declares a `relationship` field and gets a working picker with zero wiring. `keywords` is fully framework-owned the same way, see `../collections/CLAUDE.md`'s keyword-pool section for the component.

`admin` (every `BaseFieldConfig`): `admin.description` is helper text under a field's label, the one place a field-level description lives now (the old top-level `description` key is gone from the field configs); `admin.position: 'sidebar'` moves a top-level field into the fixed right-hand sidebar column `createFlatFieldsRenderer` (`renderer.tsx`, used for a global with no tabs) splits into, `'default'`/omitted stays in the main column. Only *top-level* fields participate: a `sidebar` flag inside a `row`/`group`'s own `fields` is ignored (only a named field has `admin` at all, and the split happens once, at the flat-fields level). **`createFieldsRenderer`'s own tabbed layout (a collection, or a global with tabs) does not do this split**: every tab renders its fields in one flat column regardless of `admin.position`, a real, disclosed gap, not an oversight, `CollectionForm`/`GlobalForm`'s own wrapper stays a fixed `md:max-w-lg` either way. `admin.hidden` removes a field from the rendered form entirely (`renderer.tsx`'s `renderField` returns `null` before computing `name`) while it still participates in schema/default-value derivation, unlike the dedicated `hidden` field *type* (a value with no UI concept at all). `admin.autoComplete`/`admin.rtl` forward to the underlying native `<input>`/`<textarea>`'s `autocomplete`/`dir` attributes, only meaningful for the `Input`/`Textarea`-backed leaf types (`text`, `textarea`, `email`, `password`, `confirmPassword`, `slug`; `Slug` hardcodes `autoComplete='off'` itself, so only `rtl` reaches it), a no-op everywhere else.

**Field-level `validate`** (`BaseFieldConfig['validate']`, every leaf type): `(value: unknown) => true | string`, wired into `fieldsToSchema` as a `.superRefine` on top of the field's own base schema, *before* `.optional()` wraps it, so an empty optional field never invokes it at all (zod's own `undefined` short-circuit). Deliberately scoped down from Payload's real `validate` signature: no `siblingData`/whole-document access, a field can only see its own value, matching the boundary `confirmPassword`'s own doc comment already draws (the "must match its sibling" rule stays a whole-document `.refine()`, not something a field's own `validate` could express anyway).

**Deliberately not built yet, tracked as one group of related follow-ups**: `join` (virtual/computed, Payload stores nothing new for it, a live reverse-relationship query at read time, needs a real new `content-queries.ts` function plus SQL support for arbitrary-field querying into a document's own `data` JSON blob), field-level `unique`/`index` (blocked on the same "everything lives in one opaque `data` blob" constraint every collection/global's content table has, see `../db/CLAUDE.md`), field-level conditional visibility (`admin.condition`, needs the renderer to read live sibling-field values via the form's own store), `virtual` fields, field-level `hooks`/`access` (collection-level versions of both exist, see `../collections/CLAUDE.md`; a field-level equivalent needs the same real design pass this list's other items do), and `hasMany` on a primitive like `select`/`radio` (unlike `relationship`/`blocks`, whose `hasMany` reuses the exact same picker with an array flag, `select`'s vendored primitive is single-value only, a real multi-select UI is a new `packages/ui` component, not a wiring change). None of these exist yet; each needs its own real design pass, not a mechanical field-type addition like `validate`/`admin.hidden`/`admin.autoComplete`/`admin.rtl` above.

**Tabs are a UI grouping only, not a schema-nesting concept.** A field's `name` is resolved relative to its own tab via `withTabPrefix` (`schema.ts`): `tab: 'post'` plus `name: 'content'` gives real path `post.content`; the prefix is skipped when the field's name already equals its tab id.

**`defaultValues` is never hand-written.** `deriveDefaultValues` (`schema.ts`) walks a collection/global's fields and only sets a value when a field explicitly has `defaultValue`, or is one of the container types that default to an empty container (`array`/`blocks`/`menu` → `[]`, `meta` → `{title: '', description: ''}`).
