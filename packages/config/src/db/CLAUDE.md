# CLAUDE.md: `packages/config/src/db`

Loads when working under `packages/config/src/db/`: content persistence (real D1), the local-first draft system, the global keyword pool, and the real server-backed `users` collection. See `packages/config/CLAUDE.md` for this package's other conventions.

#### The global keyword pool

`registerKeyword`/`useGlobalKeywordSuggestions`/`publishKeywordPool` (`db/collections.ts`) are **not** their own collection, the shared, site-wide keyword pool *is* the `keywords` global's own document (id `'keywords'` in `draftGlobalsCollection`/`globalsCollection`, see "Real local-first drafts" below). `registerKeyword(value)` only ever writes to the *draft*, typing a new keyword on some unrelated document's `meta`/`relations` field must never fire a real `/api/globals/keywords` write on every keystroke, same local-first invariant every other edit follows. `publishKeywordPool()` is the one place that draft ever reaches the real backend, called from `CollectionForm`'s `runPublish`, right after a document's own publish succeeds, so a newly-typed keyword goes live *with* whatever document introduced it, not via a separate manual trip to `/admin/keywords`. `useGlobalKeywordSuggestions()` reads the draft pool (falling back to and lazily seeding from whatever's already published, the first time any admin screen touches keywords in a given browser) so a keyword typed moments ago on another open document shows up as a suggestion immediately.

#### The real, server-backed `users` collection (`auth: true`)

`users` is one of two persistence models a collection can have, real accounts through better-auth's `admin()` plugin via `authClient.admin.*`, as opposed to every other collection's real D1-backed content (see "Content persistence" below). Everything below lives in `db/collections.ts` unless noted:

- **`RealUserRow`** is a closed type listing only the fields this library cares about; `toUserDocumentRow(user)` destructures the known fields out and spreads `...rest` into `data` regardless, so an app-added field flows through with zero library changes.
- **Creation bypasses `collection.insert()` entirely**, `createRealUser(collection, input)` calls `authClient.admin.createUser(input)` directly and writes the *confirmed* row via `collection.utils.writeInsert(...)`, because a client-generated temp id can never match the server-assigned real id. `AuthWidget` (`../admin/widgets/auth-widget.tsx`) is `CollectionTable`'s create-button replacement for `auth: true` collections.
- **`onUpdate` sends a real diff, not the whole document**, `Object.is`-compares `mutation.original.data`/`mutation.modified.data` per key (always excluding `title`/`slug`/`password`), skips the API call entirely if nothing changed.
- **Publish-only, same as every other collection now**, `useDocument()` never writes to the real backend on its own; editing only ever touches the local `localStorage` draft (`draftCollections`/`draftGlobalsCollection`, see "Real local-first drafts" below), and the *only* function that ever reaches `/api/<collection>` is `publish()`. `auth: true` collections keep their one "Commit & push" button; every other collection gets Publish/Update (plus Unpublish once published), there's no separate "Save" button anymore, since an edit is already persisted (to `localStorage`) the moment it's made. **"Publish" relabels to "Update"** once a document already has a remote row *and* is already `published` (`../admin/views/document/collection-form.tsx`'s `alreadyPublished`), same button, same `publish('published')` call underneath, just a label that matches "pushing an edit to something already live" instead of always saying "Publish."
- **Users aren't a relatable content type**, `RelationshipField`'s `useRelationshipOptions` deliberately excludes `'users'`.
- **`unwrap<T>({data, error})`** throws `error` directly if it's already an `Error`, else extracts `.message` if present, else `JSON.stringify`s it.
- If you're chasing a "list users" request that never resolves, check the installed `@better-auth/drizzle-adapter` version first, rc.1's unfiltered `findMany` had a real upstream bug fixed in rc.2.

#### Content persistence: real D1, one table per collection/global, raw SQL

Every collection/global except `users` is real, server-backed content, a D1-backed database, `DB` (shared with better-auth's own tables, see `templates/basics/wrangler.jsonc` for why/how they were merged). **Every collection/global gets its own real SQL table now, generated from whatever a consumer has actually registered** (not one shared `documents`/`globals` table keyed by a `collection` column). Every content table's real SQL name is `cn-`-prefixed, not the bare slug (`pages` → `cn-pages`, `form-submissions` → `cn-form-submissions`, just "prepend `cn-`", no case conversion in either direction, since a slug is already kebab-case; the *JS variable name* exported for that table in the generated schema file is still camelCase, e.g. `export const formSubmissions = sqliteTable('cn-form-submissions', ...)`, `content-schema.ts`'s `toVarName()`, kept deliberately independent of the real SQL name): `db/table-name.ts`'s `contentTableName()`/`slugFromContentTableName()` are the one shared forward/reverse transform, used by both `content-schema.ts` (schema-gen time) and `content-queries.ts` (request time) so they can never drift apart; the prefix exists specifically so a content table can never collide with whatever tables better-auth's own plugins add later, now that both live in the same database. The query layer is raw SQL (`drizzle-orm`'s own `sql`/`sql.raw` tag, not Drizzle's typed relational query builder) against a table name resolved dynamically at runtime, this package can't import a consumer's generated table objects (they don't exist at library-compile-time), so real table-name safety comes from `quoteIdent()` (identifier-shape validation) plus letting SQLite's own "no such table" error surface as `UnknownTableError`, not from static typing.

- **Schema generation, queries, and the Hono route all live in the library** (`content-schema.ts`/`content-queries.ts` in `db/`, `content-route.ts` in `../api/`, see `../api/CLAUDE.md`), not in a consumer. `content-schema.ts` is a *generator*, not a fixed schema, `buildContentSchemaSource(entries)` emits one real `sqliteTable()` per collection/global slug (`id`/`title`/`slug`/`status`/`data`/`createdAt`/`updatedAt` for a collection, just `data`/`updatedAt` for a global, every field beyond those still lives in one opaque `data` JSON column, deliberately: giving every individual field its own SQL column would need a field-type-to-SQL-column mapper and reintroduce migration friction on every field edit, not just when a collection is added/removed), plus `collectionTablesBySlug`/`globalTablesBySlug` lookups and `contentRelations` (still required by this rc of `drizzle-orm` even with zero real relations). **`bun x base --config=<path> --output=<path>`** (the library's own CLI, `cli.ts`, `bin: {base: ...}` in `package.json`) is how a consumer regenerates their own copy of the content schema, it imports the consumer's `base.config.ts` for its side effect (populating `collectionsBySlug`/`globalsBySlug` via `registerBaseConfig()`), then writes the generated source. Adding/removing a collection or global means re-running this CLI and migrating, same "generate, then migrate" shape `auth:gen` already has.

  **`bun x base gen (--local | --remote) [--skip-auth] [--yes]`** (`cli.ts`'s `gen` subcommand, `cli/gen.ts`) is the full four-step orchestrator, `auth@rc generate` then the schema-gen call above then `drizzle-kit generate` then `wrangler d1 migrations apply`. Defaults match `templates/basics`'s own file layout (`src/config/api/auth/auth.ts`, `src/config/base.config.ts`, `db/schemas/{users,content}.ts`, `drizzle.config.ts`, D1 binding `DB`), a consumer whose layout differs overrides just that one flag (`--auth-config`/`--auth-output`/`--config`/`--content-output`/`--drizzle-config`/`--d1`), same convention-over-configuration trade-off as everywhere else in this package.
- **`content-queries.ts`**: `listDocuments`/`getDocument`/`createDocument`/`updateDocument`/`deleteDocument`/`listGlobals`/`getGlobal`/`upsertGlobal`/`listGlobalSlugs`, each taking a `ContentDatabase` (= `DrizzleD1Database`, structural, a consumer only ever hands this package `drizzle(env.DB, {logger: false})`, no `relations` needed at the query layer since it's raw SQL, not the relational query builder) as the first param, and every collection-scoped function takes the collection's own `slug` as a plain string (not a generated table object). `updateDocument`/`upsertGlobal` only write what changed, fixed columns get a direct `SET` clause only when provided, and the caller's own `fields`/diff object gets *merged* into the existing `data` blob (`{...existing.data, ...fields}`), never a whole-document replace; since this is raw SQL rather than Drizzle's typed table API, `$onUpdate()`-style JS-side column defaults don't fire for free, every write sets `updatedAt` explicitly (real SQL-level defaults like `createdAt`'s own `DEFAULT (...)` clause still apply automatically). `listDocuments` supports a narrow `where`/`limit`/`page` (top-level columns only, `status`/`slug` via `equals`, not arbitrary JSON-field querying) and returns a Payload-style paginated envelope (`{docs, totalDocs, limit, page, totalPages, hasNextPage, hasPrevPage}`). `listGlobalSlugs(db)` answers "which globals exist" by asking the live database directly (`sqlite_master` plus `pragma_table_info`, looking for tables with a `data` column but no `status` column) rather than a JS-side registry, see `UnknownTableError`'s own doc comment in that file for why: a registry-based check raced Vite's own lazy per-route module loading in dev and produced a real, empirically-confirmed false 404 on a cold first request.
- **`content-route.ts`** (`../api/`): `createContentRoute(db)`, a Hono factory (not a pre-built app), **takes only `db`**, no registry, no consumer-side list of valid slugs; an unrecognized collection surfaces as `UnknownTableError`, caught by the route's own `.onError()` handler and turned into a 404. See `../api/CLAUDE.md` for the mounting/routing details.
- **The consumer's entire runtime footprint for this is one export**: `db/db.ts`'s `contentdb` is `drizzle(env.DB, {logger: false})`, no `relations` import, no generated-schema import at all (the generated `db/schemas/content.ts` is read only by `drizzle-kit` at migration time). `createHandler({db: contentdb, ...})` (see `../api/CLAUDE.md`) is what actually wires `contentdb` into the mounted API.
- **Client side, remote/published documents**: `contentCollections`/`globalsCollection` (`db/collections.ts`) are real `queryCollectionOptions` (tanstack-db) backed by a real `ContentApiClient` (Payload-Local-API-named methods, `find`/`findByID`/`create`/`update`/`delete`/`findGlobal`/`updateGlobal`). **`baseConfig()` builds this RPC client itself now** (`define.ts`), typed against this package's own exported `BaseConfigRouteType` (`../api/route.ts`) directly: `hc<BaseConfigRouteType>(apiOrigin + '/api', {init: {credentials: 'include'}})`, where `apiOrigin` is `window.location.origin` in an actual browser (always correct, no custom-domain/dev-port drift) or the consumer's own `hostDomain` prop as an SSR-only fallback. `staleTime: Infinity`, explicit `collection.utils.writeInsert`/`writeUpdate`/`writeDelete` after a mutation resolves (the mutation's own response is already the authoritative row, no follow-up `refetch()` GET, an earlier version called `refetch()` here, which was the actual cause of a real "too many requests" bug, one full list re-fetch after every single write). `globalsCollection` specifically needs a `createLazyCollection()` Proxy helper, it's query-backed, so it needs `registerContentDataSource()` (called inside `baseConfig()`) to have already run first, which isn't guaranteed at module-eval time, the Proxy defers actual creation to first property access. A ready-to-import `base` object (`db/content-client.ts`, exported from `@baseconfig/core`'s barrel) wraps the same client as TanStack Query `queryOptions()`/`mutationOptions()`, `useQuery(base.find({collection: 'posts'}))`, `useMutation(base.createMutation('posts'))`, for application code outside the admin engine's own collections.
- **Real local-first drafts, `draftCollections`/`draftGlobalsCollection`**, the actual thing that makes editing free of network calls. Built via `@tanstack/db`'s own `localStorageCollectionOptions({storageKey: 'base-config:draft:<slug>', getKey: (item) => item.id})` (re-exported from `@tanstack/react-db`, already a real dependency), with **no `onInsert`/`onUpdate`/`onDelete` at all**, so every mutation against one of these is a pure `localStorage` write, zero network, always. `db/use-document.ts`'s `useDocument({collection, draftCollection, id, schema, defaultValues})` is the only thing that reads/writes these directly: it seeds a draft from the remote row's data (or `defaultValues()` for a brand-new document) the first time a document is opened, write-throughs every form edit into the draft (no debounce, it's free), and exposes `publish(statusOverride)` as the **one and only** function that ever reaches the real `/api/<collection>` backend, reading the draft's current data and calling `collection.insert()`/`collection.update()` on the *remote* collection (insert vs. update decided by whether a remote row exists yet). `CollectionForm`/`GlobalForm` have no "Save" button anymore, editing already persists (to `localStorage`) the moment it happens; Publish/Unpublish/"Commit & push" are the only actions, all calling `publish()`. **Caller precondition**: a component calling `useDocument` must not mount until both `collection` and `draftCollection`'s own `useLiveQuery(...).isReady` are true (`CollectionForm`'s `CollectionFormLive`/`GlobalForm`'s `GlobalFormLive` gate on exactly this), `useAppForm` only snapshots `defaultValues` once, at first render, so mounting earlier freezes fields at empty/default values that never get replaced once real data arrives (a real, confirmed bug: a Base UI "uncontrolled to controlled" warning, and a document that looked empty despite having real remote data).
- **`db/deep-equal.ts`'s `deepEqual()` is the one shared equality check for a document/global's own `data`**, used in three places that each independently, and subtly, got this wrong before: `useDocument`'s own `isDirty` and `publishKeywordPool`'s remote-vs-draft check both used to compare via `JSON.stringify(a) === JSON.stringify(b)`, which is sensitive to object key *order*, not just content, so both routinely reported "changed" when nothing had (the Publish button showing enabled right after a successful publish with no further edits; keywords appearing to re-publish on every unrelated document publish). `contentCollections`'/`globalsCollection`'s own `onUpdate` diffing used to compare per-field via `Object.is()`, which compares object/array-valued fields *by reference*: `mutation.modified`/`mutation.original` are two independently-sourced object graphs (client-reconstructed vs. server-fetched) that were never the same reference to begin with, so every composite field (`blocks`, `meta`, `array`, `relations`, `menu`, `keywords`, ...) was *always* included in the diff sent to the server regardless of whether it actually changed; only primitive-valued fields genuinely benefited. All four call sites now use `deepEqual()` instead.
- **Every UI surface that shows "what does this document currently look like" has to consider the draft, not just the remote row, three real, previously-buggy instances of this, all fixed the same way.** (1) `CollectionTable`'s list view merges in `draftOnlyRows` (draft rows with no matching remote `id`) alongside real rows, so a document that's been drafted but never published still shows up (with a "Draft" status badge) instead of disappearing the moment you navigate away from it, remote data wins whenever a row exists in both places, so the list doesn't visually shift under someone editing the same document in another tab. Its per-row Delete button is row-aware for the same reason: a draft-only row's `id` isn't in the remote collection, so it deletes from `draftCollections[slug]` instead of calling `collection.delete()`. (2) `CollectionForm`'s `DocumentEditor` exposes a "Discard draft" (no remote row exists yet, deletes the local draft and navigates back to the list) / "Revert changes" (a remote row exists and the draft differs, resets the draft's `data` back to `remoteRow.data`, then navigates with `reloadDocument: true`, since `useAppForm` snapshots `defaultValues` once and won't otherwise re-render already-mounted fields) action, gated on `useDocument()`'s own `hasRemoteRow`, distinguishes "brand-new, nothing to revert to" from "published elsewhere, with local edits on top"; `isDirty` alone can't tell these apart, since it's `true` in both cases. (3) `Topbar`'s breadcrumb (`../admin/views/topbar.tsx`'s `ItemBreadcrumbLive`) reads both `contentCollections[slug]` and `draftCollections[slug]`, preferring the draft's own `slug`, the *opposite* precedence from the list view, deliberately: you're actively typing in this document right now, so the breadcrumb should track what you're typing, not the last-published snapshot. Before this fix, all three only ever read the remote collection, which is what made local-first editing feel like it was silently forcing a publish, a document with no remote row yet was simply invisible/unreachable/stuck-on-"untitled" everywhere outside the open editor itself.

- **Migrations**: one unified `drizzle.config.ts` (`schema: ['./db/schemas/users.ts', './db/schemas/content.ts']`, `out: '.migrations/'`), applied via `db:gen`/`db:local`/`db:remote`, see `templates/basics/drizzle.config.ts` for the same shape in a real consumer.
- **A known, benign console warning**: `[cleanupQueryIfIdle] Invariant violation: refcount=1 but no listeners`, this comes from `@tanstack/query-db-collection` itself (`dist/esm/query.js`), not this app's code. In `eager` sync mode it increments its own internal `queryRefCounts` once at sync-start and never decrements it (`unloadSubset` is unset); listener attach/detach is driven separately, purely by subscriber count. Once a query's last listener unmounts and React Query's own idle GC later evicts that now-listener-less query, the refcount bookkeeping is already stale and the library logs this warning, a real decoupling inside the library, confirmed by reading its source, not something fixable from application code. It tends to fire whenever a whole admin section unmounts at once (e.g. a hard-reload sign-out).

#### The circular-import trap (read this before touching `../collections/registry.ts`/`db/collections.ts`)

`collections/registry.ts` is a **passive store** (`collectionsBySlug`/`globalsBySlug` start empty; `registerBaseConfig(collections, globals)` populates them), it does **not** import a consumer's own `base.config.ts`. If it did: `base.config.ts` → its collection files → `defineCollection`/`defineGlobal` (`@baseconfig/core`) → `RelationshipField`/`NavMenuField` (composite fields) → `contentCollections` (`db/collections.ts`) → `registry.ts` → back to `base.config.ts`. That cycle is real and throws a hard TDZ crash under Bun's/Node's native ESM loader, Rollup/Vite happen to tolerate it, which is *why* it went unnoticed. `base.config.ts` (via `baseConfig()`) pushes into the registry; nothing pulls the app's config into the framework layer.

**A related, once-real bug for the same reason**: a server-only `createHandler()` call site and a consumer's own `base.config.ts` (where every `Plugin`, e.g. `@baseconfig/plugin-form-builder`'s `formBuilderPlugin()`, actually registers its `endpointFactories`/`hooks`/`blocks` via `baseConfig()`) are two completely separate module graphs, each only loaded when its own route is first hit. `createHandler()` reads `collectEndpointFactories()`/`collectHooks()` **synchronously, once**, at its own module-eval time, if nothing has forced `base.config.ts` to evaluate on the server first, that read sees an empty registry, and a plugin's own endpoint 404s forever for that isolate (confirmed with a real repro: a fresh dev server, first request straight at a plugin's endpoint, 404 in ~1ms, a pure routing miss, not a real 404). The fix is one line: a consumer's own API entry needs a side-effect-only `import './config/base.config'` before its own `createHandler()` call, guaranteeing `baseConfig()` has already run. Safe to add, ES modules cache by specifier, so this doesn't double-run `baseConfig()`'s side effects even though the admin UI's own routes also import the same file.
