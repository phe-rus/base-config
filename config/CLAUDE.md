# CLAUDE.md — `base/config`

Internals of the `@baseconfig/core` engine — loads only when a session is working with files under `base/config/src/`. See the root `CLAUDE.md` for the boundary between this library and `www/src/config/` (the consumer), the three factories' basic shape, and the annotated directory tree.

#### Three admin namespaces: `RenderView`, `ContextView`, `ProviderView`

All three live under `admin/views/`. `RenderView` and `ContextView` are a plain function component with named sub-parts hung off it as properties (`export const X: XComponent = (...) => ...; X.Sub = (...) => ...`, typed via an intersection cast); `ContextView`/`ProviderView` are plainer — a bare object of named component references, since nothing ever renders `<ContextView>`/`<ProviderView>` directly, only their members:

- **`RenderView`** (`admin/views/render-view.tsx`) is markup-level reuse: the page-container chrome every top-level admin view shares. `RenderView` itself is the outer `<article className='container flex flex-col w-full md:max-w-4xl mx-auto gap-5 py-5'>`; `.Header`, `.NotFound`, `.List` (a titled grid of link cards), `.Breadcrumb`, `.FolderCard`/`.FileCard` (Storage's grid rows) are the named sub-parts.
- **`ContextView`** (`admin/views/dispatch/context-view.tsx`) is route-dispatch-level grouping: `{Dashboard, Entry, Storage}`. **`ContextView.X` must never be written directly as a route's `component:`** — every consumer route destructures to a local const first (`const { Entry } = ContextView` then `component: Entry`).
- **`ProviderView`** (`admin/views/dispatch/provider.tsx`) is `{Context}` — one member, `ProviderView.Context`, the component a consumer wraps the `$collection` layout route's `Outlet` in. It resolves `RouteViewState` once per navigation and provides it via `useRouteView()`. Unlike `ContextView` members, `<ProviderView.Context>` is used as plain JSX inside a route file's own component body, not as a route's `component:` value.

#### The three factories (`base/config/src/define.ts`)

- **`defineCollection({slug, label?, color?, path?, auth?, columns?, filterKey?, admin?, tabs})`** → a full `CollectionConfig` (`schema`, `defaultValues`, `Fields` all derived automatically from `tabs`). `label` is optional (derived via `labelFromSlug(slug)` if omitted). `path` sets the collection's public URL prefix. `auth: true` marks the real, server-backed `users` collection — every other collection is real D1-backed content (see "Content persistence" below). `columns`/`filterKey` control `CollectionTable`'s columns. `admin.useAsTitle` names a real field to display as a document's "title" for collections without one (`users` uses `name`).
- **`defineGlobal({slug, label?, fields})`** → a full `GlobalConfig`, same derivation, minus tabs. **Or** `defineGlobal({slug, label?, component})` → a `custom: true` global whose `Fields` is `component` directly, with no schema/document/`GlobalForm` wrapper — `admin/views/dispatch/provider.tsx`'s `resolveRouteView` checks the generic `config.custom` flag and resolves it to `mode: 'custom'`, which `ContextView.Entry` renders as the whole page. For a global that isn't really a document to edit — e.g. Storage.
- **`baseConfig({queryClient, auth?, config, collections, globals, ...})`** → identity function with several side effects: registers every `collections`/`globals` entry with `base/config/src/collections/registry.ts`; registers `queryClient`/`contentClient`/`storageClient` unconditionally via `registerContentDataSource()`/`registerStorageDataSource()` (every consumer needs real content persistence, not just `auth`-enabled ones); if `auth` is passed, calls `registerUsersDataSource({queryClient, authClient: auth})`. Returns the same config either way.

#### Field types (`base/config/src/fields/types.ts`)

Primitives (dispatched generically to a matching `@baseconfig/ui/forms` control — see `base/ui/CLAUDE.md` for the full, much larger current vocabulary): `text`, `textarea`, `richtext`, `checkbox`, `switch`, `date`, `keywords`, `upload`, `select`, `radio`, plus the newer leaf types `email`/`number`/`password`/`confirmPassword`/`hidden`/`code`/`json`/`slug`/`point` (not yet all wired into this union — see `base/ui/CLAUDE.md`'s field-type table for exactly which `@baseconfig/ui/forms` components exist vs. which have a corresponding `FieldConfig` variant here; adding the `FieldConfig` union entry + resolver wiring for one is a small, mechanical follow-on, not yet done for most of them). `array` recurses (its own `fields` describe one item's shape; nested array item paths compose via `${path}.${field.name}`).

Composites (each dispatched directly to an app-supplied component via `define.ts`'s resolver maps, not through the generic primitive switch): `blocks` (page-content blocks), `relationship` (single/multi document reference), `relations` (the "related posts" manual-or-keyword-filter composite), `meta` (SEO title/description/image/keywords bundle), `menu` (nav menus), `links` (a repeatable per-item label + button appearance + link-target list — shared with `menu`'s own per-item link fields, see "Nav menus and the shared link fields" below).

**Layout/grouping field types** (Payload-modeled): `row`/`collapsible` (`{type, fields}`, no `name` — pure presentational grouping, fields splice flat into the parent object exactly as if the container weren't there), `group` (`{type: 'group', name?, label?, description?, fields}` — nests under `name` if given, splices flat if omitted, matching Payload's own real behavior), `tabs`-as-a-field (`{type: 'tabs', tabs: [{id, label, name?, fields}]}` — each sub-tab independently named/unnamed, same nest-or-splice rule as `group`; scoped to a single level in this pass, a sub-tab's own fields can freely use `row`/`collapsible`/`group` but not a second nested `tabs`-as-field), `ui` (`{type: 'ui', Component: FC}` — a blank, data-free admin-only slot, contributes nothing to schema/defaultValues). All five are resolved away by `fields/schema.ts`'s `expandFields()` (idempotent — safe on both a raw field list and an already-flattened one) before any real schema/defaultValue derivation ever sees them, and `isContainerFieldType()` (`fields/types.ts`) is the single source of truth both `schema.ts` and `renderer.tsx` key off to avoid the type list drifting between the two files. `fields/renderer.tsx`'s `renderField` dispatches all five as early-return branches *before* it computes `field.name` (which none of them have) — `row` renders a flex row, `collapsible` wraps `@baseconfig/ui`'s `Collapsible`/`CollapsibleTrigger`/`CollapsibleContent`, `group` renders a `<fieldset>` with an optional `<legend>`, `tabs`-as-field renders nested `Tabs`/`TabsList`/`TabsContent` chrome per sub-tab, `ui` renders `field.Component` directly — none of the five use `form.AppField` themselves (that only ever wraps a real, named leaf field further down the recursion).

**`join` doesn't exist yet, deliberately.** Unlike the five above, it's virtual/computed (Payload stores nothing new for it — a live reverse-relationship query at read time), needing a real new `content-queries.ts` function plus SQL support for arbitrary-field querying into a document's own `data` JSON blob — a materially bigger feature than a field-type add, not attempted in the same pass.

**Tabs are a UI grouping only, not a schema-nesting concept.** A field's `name` is resolved relative to its own tab via `withTabPrefix` (`fields/schema.ts`): `tab: 'post'` + `name: 'content'` → real path `post.content`; the prefix is *skipped* when the field's name already equals its tab id.

**`defaultValues` is never hand-written.** `deriveDefaultValues` (`fields/schema.ts`) walks a collection/global's fields and only sets a value when a field explicitly has `defaultValue`, or is one of the container types that default to an empty container (`array`/`blocks`/`relations`/`menu` → `[]`, `meta` → `{title: '', description: ''}`).

#### Relationships (`base/config/src/collections/fields/relationship-field.tsx`)

A selected relationship stores `{id, slug, title}` (`RelationshipValue`), not a bare id. The picker itself queries **every real collection via a fixed number of `useLiveQuery` calls** (`pages`/`posts`/`policies`, one each) — adding a fourth collection means adding one more explicit `useLiveQuery` line in `useRelationshipOptions`. `hasMany` switches between `RelationshipFieldSingle` (plain combobox) and `RelationshipFieldMulti` (chips).

#### Nav menus and the shared link fields (`menu`/`links` field types, `base/config/src/collections/fields/{nav-menu-field,links-field}.tsx`)

`links-field.tsx` is the shared foundation both nav menus and content blocks build on:

- **`LinkModeFields({form, name})`** — a link's own mode/target/open-in-new-tab: `mode: 'internal'` (a `RelationshipField` reference — picking one auto-syncs `to` via `collectionPath(collectionsBySlug[value.collection], value.slug)`) or `mode: 'custom'` (hand-typed `to`), plus `openInNewTab`. Deliberately excludes `label`/`appearance` — those are a *caller's* own per-item fields (see `LinksField` below and `NavMenuField`'s own `NavItemFields`), not part of a link's mode/target itself.
- **`LinksField({form, name, label?, description?})`** — wraps `LinkModeFields` in an `ArrayField`: each item gets its own `label` + button `appearance` (the real shadcn `Button` variants, `appearanceValues`) alongside the mode/target fields. This is `type: 'links'`'s (`fields/types.ts`'s `LinksFieldConfig`) real implementation, and is also imported *directly* by the `cta`/`banner` blocks (`collections/blocks/{cta,banner}.tsx`) rather than going through the generic per-field-type dispatch — the same "a block reuses a composite field component directly" pattern `relatedPosts` already uses for `RelationGroupFields`. No mega-menu option — that's `NavMenuField`'s own extra complexity, deliberately not part of this plainer, array-only field. `ArrayField`'s own default row label already works here for free, since every item has a real `label`.

`nav-menu-field.tsx` (`menu` field type) is used by both `footer` and `topbar`. Every item is a **link by default** — `NavItemFields` renders its own `label`/`appearance`/`openInNewTab`, then delegates the mode/target part to `LinkModeFields` above (`NavLinkModeFields`'s non-disabled branch calls it directly, rather than duplicating the reference/custom-URL logic a second time). Checking **"Mega menu"** drops the link fields and shows a **"Category"** toggle instead. There is no public-facing render of any of this yet — this is authoring-side only.

#### Page-content blocks (`base/config/src/collections/blocks/`)

**`blocksBySlug` (`registry.ts`) is a live, runtime `Record<string, BlockConfig>`, not a closed union** — mirrors `collections/registry.ts`'s own `collectionsBySlug`/`globalsBySlug` pattern, for the same reason: a plugin package (e.g. `@baseconfig/plugin-form-builder`) can't add a member to a union type it doesn't own, so this needs to be something it can register *into* via `registerBlocks(blocks)` (called once by `baseConfig()` with `config.blocks ?? []`). Seeded eagerly with this package's own 7 built-in blocks (unlike `collectionsBySlug`, these aren't optional — a consumer gets them for free with zero registration): `richtext`, `media`, `cta`, `banner`, `grid`, `code`, `relatedPosts`. A slug collision silently overwrites the built-in (last write wins, no error) — the same collision behavior `collectionsBySlug`/`globalsBySlug` already have.

- **`columns` was removed, its role fully absorbed by `grid`** — a fixed 2-column layout was just a narrower special case of what `grid` already needed to be (a general "compose blocks visually" primitive, not two overlapping ones). `grid`'s own schema validates its nested `items` loosely (`z.object({blockType: z.string()}).loose()`, to avoid a circular schema reference back to the full block union) and its `Render` recursively dispatches each item through `blocksBySlug[item.blockType]`'s own `Render`, wrapped in a `variant`-controlled layout (`default`/`card`/`bordered` — cosmetic only, no effect on the admin editor's own plain list view).
- **`media` dropped `alt`/`caption` entirely** — the real upload value's own `name`/`url`/`size` already covers what those stood in for; this block is just an image (`{blockType: 'media', image: uploadValueSchema.optional()}`). It's also the one block left without a public `Render` — see the root `CLAUDE.md`'s "Not done yet".
- **`cta`/`banner` both use `LinksField`** (see "Nav menus and the shared link fields" above) instead of a single `buttonLabel`/`link`/`variant` triplet — `links: linksSchema.optional()`, rendered publicly as one `<a className={buttonVariants({variant: link.appearance})}>` per item.
- **`code`** — a real CodeMirror 6 editor (`@baseconfig/ui`'s `CodeEditor`/`Code` field, see `base/ui/CLAUDE.md`), not a plain textarea. `language`/`code` are sibling fields, but the language select itself lives inline in the editor's own top-right corner (`f.Code`'s `languages`/`onLanguageChange` props) rather than as a separate visible field — the nested-`form.AppField` pattern (`language` field's render callback wraps the `code` field's own) is the same one `nav-menu-field.tsx` already uses to let one field's rendering react to a sibling's *current* value. A modest `looksLikeJson()` heuristic (parses on every keystroke) auto-switches `language` to `'json'` when the pasted/typed content looks like it — deliberately not real language detection, just the one case that's realistically detectable without a parser or a new dependency. `Render` builds a one-node tiptap doc (`{type: 'codeBlock', attrs: {language}, content: [...]}`) and renders it through `@baseconfig/ui/basiccn/preview`'s `Preview`, reusing the editor's own existing `CodeBlockLowlight` syntax highlighting rather than a second highlighting path. `lowlight`'s `common` bundle only registers `typescript`/`javascript`/`json` by name (no separate `tsx`/`jsx` grammar), so both map onto their non-JSX sibling for highlighting purposes — still real, readable highlighting, just not JSX-attribute-aware.
- The **`JSON` field** (`@baseconfig/ui/forms`) shares the same `CodeEditor` as `Code` but commits *parsed* JSON rather than a string — see `base/ui/CLAUDE.md`'s field vocabulary for the real distinction.

#### The global keyword pool

`registerKeyword`/`useGlobalKeywordSuggestions`/`publishKeywordPool` (`base/config/src/db/collections.ts`) are **not** their own collection — the shared, site-wide keyword pool *is* the `keywords` global's own document (id `'keywords'` in `draftGlobalsCollection`/`globalsCollection`, see "Real local-first drafts" below). `registerKeyword(value)` only ever writes to the *draft* — typing a new keyword on some unrelated document's `meta`/`relations` field must never fire a real `/api/globals/keywords` write on every keystroke, same local-first invariant every other edit follows. `publishKeywordPool()` is the one place that draft ever reaches the real backend — called from `CollectionForm`'s `runPublish`, right after a document's own publish succeeds, so a newly-typed keyword goes live *with* whatever document introduced it, not via a separate manual trip to `/admin/keywords`. `useGlobalKeywordSuggestions()` reads the draft pool (falling back to and lazily seeding from whatever's already published, the first time any admin screen touches keywords in a given browser) so a keyword typed moments ago on another open document shows up as a suggestion immediately.

#### The real, server-backed `users` collection (`auth: true`)

`users` (`www/src/config/collections/users.ts`) is one of two persistence models a collection can have — real accounts through better-auth's `admin()` plugin via `authClient.admin.*`, as opposed to every other collection's real D1-backed content (see "Content persistence" below; earlier states of this doc described every non-`users` collection as `localStorage`-only — that's no longer true). Everything below lives in `base/config/src/db/collections.ts` unless noted:

- **`RealUserRow`** is a closed type listing only the fields this library cares about; `toUserDocumentRow(user)` destructures the known fields out and spreads `...rest` into `data` regardless, so an app-added field flows through with zero library changes.
- **Creation bypasses `collection.insert()` entirely** — `createRealUser(collection, input)` calls `authClient.admin.createUser(input)` directly and writes the *confirmed* row via `collection.utils.writeInsert(...)`, because a client-generated temp id can never match the server-assigned real id. `AuthWidget` (`admin/widgets/auth-widget.tsx`) is `CollectionTable`'s create-button replacement for `auth: true` collections.
- **`onUpdate` sends a real diff, not the whole document** — `Object.is`-compares `mutation.original.data`/`mutation.modified.data` per key (always excluding `title`/`slug`/`password`), skips the API call entirely if nothing changed.
- **Publish-only, same as every other collection now** — `useDocument()` never writes to the real backend on its own; editing only ever touches the local `localStorage` draft (`draftCollections`/`draftGlobalsCollection`, see "Real local-first drafts" below), and the *only* function that ever reaches `/api/<collection>` is `publish()`. `auth: true` collections keep their one "Commit & push" button; every other collection gets Publish (+ Unpublish once published) — there's no separate "Save" button anymore, since an edit is already persisted (to `localStorage`) the moment it's made.
- **Users aren't a relatable content type** — `RelationshipField`'s `useRelationshipOptions` deliberately excludes `'users'`.
- **`unwrap<T>({data, error})`** throws `error` directly if it's already an `Error`, else extracts `.message` if present, else `JSON.stringify`s it.
- If you're chasing a "list users" request that never resolves, check the installed `@better-auth/drizzle-adapter` version first — rc.1's unfiltered `findMany` had a real upstream bug fixed in rc.2.

#### Content persistence: real D1, one table per collection/global, raw SQL

Every collection/global except `users` is real, server-backed content — a D1-backed database, `BASECONFIG` (see the root `CLAUDE.md`'s "Database" section). **Every collection/global gets its own real SQL table now, generated from whatever a consumer has actually registered** (not one shared `documents`/`globals` table keyed by a `collection` column — that was an earlier, now-superseded design; if older notes describe a shared table, that's stale). The query layer is raw SQL (`drizzle-orm`'s own `sql`/`sql.raw` tag, not Drizzle's typed relational query builder) against a table name resolved dynamically at runtime, not Drizzle's typed table API — this package can't import a consumer's generated table objects (they don't exist at library-compile-time), so real table-name safety comes from `quoteIdent()` (identifier-shape validation) plus letting SQLite's own "no such table" error surface as `UnknownTableError`, not from static typing.

- **Schema generation, queries, and the Hono route all live in the library** (`base/config/src/db/{content-schema,content-queries,content-route}.ts`), not in `www`. `content-schema.ts` is a *generator*, not a fixed schema — `buildContentSchemaSource(entries)` emits one real `sqliteTable()` per collection/global slug (`id`/`title`/`slug`/`status`/`data`/`createdAt`/`updatedAt` for a collection, just `data`/`updatedAt` for a global — every field beyond those still lives in one opaque `data` JSON column, deliberately: giving every individual field its own SQL column would need a field-type→SQL-column mapper and reintroduce migration friction on every field edit, not just when a collection is added/removed), plus `collectionTablesBySlug`/`globalTablesBySlug` lookups and `contentRelations` (still required by this rc of `drizzle-orm` even with zero real relations). **`bun x base --config=<path> --output=<path>`** (the library's own CLI, `base/config/src/cli.ts`, `bin: {base: ...}` in `package.json`) is how a consumer regenerates their own copy (`www/db/schemas/content.ts`) — it imports the consumer's `base.config.ts` for its side effect (populating `collectionsBySlug`/`globalsBySlug` via `registerBaseConfig()`), then writes the generated source. Adding/removing a collection or global means re-running this CLI and migrating, same "generate, then migrate" shape `auth:gen` already has for `AUTH` — never hand-edit the generated file.
- **`content-queries.ts`**: `listDocuments`/`getDocument`/`createDocument`/`updateDocument`/`deleteDocument`/`listGlobals`/`getGlobal`/`upsertGlobal`/`listGlobalSlugs`, each taking a `ContentDatabase` (= `DrizzleD1Database`, structural — a consumer only ever hands this package `drizzle(env.BASECONFIG, {logger: false})`, no `relations` needed at the query layer since it's raw SQL, not the relational query builder) as the first param, and every collection-scoped function takes the collection's own `slug` as a plain string (not a generated table object). `updateDocument`/`upsertGlobal` only write what changed — fixed columns get a direct `SET` clause only when provided, and the caller's own `fields`/diff object gets *merged* into the existing `data` blob (`{...existing.data, ...fields}`), never a whole-document replace; since this is raw SQL rather than Drizzle's typed table API, `$onUpdate()`-style JS-side column defaults don't fire for free — every write sets `updatedAt` explicitly (real SQL-level defaults like `createdAt`'s own `DEFAULT (...)` clause still apply automatically). `listDocuments` supports a narrow `where`/`limit`/`page` (top-level columns only — `status`/`slug` via `equals` — not arbitrary JSON-field querying) and returns a Payload-style paginated envelope (`{docs, totalDocs, limit, page, totalPages, hasNextPage, hasPrevPage}`). `listGlobalSlugs(db)` answers "which globals exist" by asking the live database directly (`sqlite_master` + `pragma_table_info`, looking for tables with a `data` column but no `status` column) rather than a JS-side registry — see `UnknownTableError`'s own doc comment in that file for why: a registry-based check raced Vite's own lazy per-route module loading in dev and produced a real, empirically-confirmed false 404 on a cold first request.
- **`content-route.ts`**: `createContentRoute(db)` — a Hono factory (not a pre-built app), **takes only `db`** — no registry, no consumer-side list of valid slugs; an unrecognized collection surfaces as `UnknownTableError`, caught by the route's own `.onError()` handler and turned into a 404. Mounted at the API's own root by `createBaseConfigRoute()` — a collection's real REST address is `/api/<collection>`, a global's is `/api/globals/<slug>`, matching Payload's own REST shape. Real `@hono/zod-validator` schemas gate `POST`/`PATCH` bodies and the list route's query params. Reads are public (drafts filtered out for non-admins); writes are admin-only, same `session.user.role === 'admin'` gate as storage. `/globals` is registered before the `/:collection` wildcard in the route's own chain — Hono resolves an ambiguous match by registration order, not static-vs-dynamic priority, confirmed empirically.
- **The consumer's entire runtime footprint for this is one line**: `www/db/content-db.ts` is `export const contentdb = drizzle(env.BASECONFIG, {logger: false})` — no `relations` import, no generated-schema import at all (the generated `db/schemas/content.ts` is read only by `drizzle-kit` at migration time, via `www/drizzle.content.config.ts`'s own `schema:` pointer, never by the running app). `createHandler({db: contentdb, ...})` (see the root `CLAUDE.md`'s "Backend" section) is what actually wires `contentdb` into the mounted API.
- **Client side, remote/published documents** (`base/config/src/db/collections.ts`): `contentCollections`/`globalsCollection` are real `queryCollectionOptions` (tanstack-db) backed by a real `ContentApiClient` (Payload-Local-API-named methods — `find`/`findByID`/`create`/`update`/`delete`/`findGlobal`/`updateGlobal`). **`baseConfig()` builds this RPC client itself now** (`define.ts`) — a consumer no longer hand-builds a typed `hc<TypeRouter>()` client and passes it in as `contentClient`/`storageClient` props (those props are gone from `BaseConfigProps`); since every route this client ever calls is 100% library-owned (`createBaseConfigRoute()`/`createHandler()`, no consumer-specific routes mixed in), this package types the client against its own exported `BaseConfigRouteType` (`api/route.ts`) directly: `hc<BaseConfigRouteType>(apiOrigin + '/api', {init: {credentials: 'include'}})`, where `apiOrigin` is `window.location.origin` in an actual browser (always correct, no custom-domain/dev-port drift) or the consumer's own `hostDomain` prop as an SSR-only fallback. `staleTime: Infinity`, explicit `collection.utils.writeInsert`/`writeUpdate`/`writeDelete` after a mutation resolves (the mutation's own response is already the authoritative row — no follow-up `refetch()` GET; an earlier version called `refetch()` here, which was the actual cause of a real "too many requests" bug — one full list re-fetch after every single write). `globalsCollection` specifically needs a `createLazyCollection()` Proxy helper — it's query-backed, so it needs `registerContentDataSource()` (called inside `baseConfig()`) to have already run first, which isn't guaranteed at module-eval time — the Proxy defers actual creation to first property access. A ready-to-import `base` object (`db/content-client.ts`, exported from `@baseconfig/core`'s barrel) wraps the same client as TanStack Query `queryOptions()`/`mutationOptions()` — `useQuery(base.find({collection: 'posts'}))`, `useMutation(base.createMutation('posts'))` — for application code outside the admin engine's own collections.
- **Real local-first drafts, `draftCollections`/`draftGlobalsCollection`** — the actual thing that makes editing free of network calls. Built via `@tanstack/db`'s own `localStorageCollectionOptions({storageKey: 'base-config:draft:<slug>', getKey: (item) => item.id})` (re-exported from `@tanstack/react-db`, already a real dependency — no new package), with **no `onInsert`/`onUpdate`/`onDelete` at all**, so every mutation against one of these is a pure `localStorage` write, zero network, always. `db/use-document.ts`'s `useDocument({collection, draftCollection, id, schema, defaultValues})` is the only thing that reads/writes these directly: it seeds a draft from the remote row's data (or `defaultValues()` for a brand-new document) the first time a document is opened, write-throughs every form edit into the draft (no debounce — it's free), and exposes `publish(statusOverride)` as the **one and only** function that ever reaches the real `/api/<collection>` backend — reading the draft's current data and calling `collection.insert()`/`collection.update()` on the *remote* collection (insert vs. update decided by whether a remote row exists yet). `CollectionForm`/`GlobalForm` have no "Save" button anymore — editing already persists (to `localStorage`) the moment it happens; Publish/Unpublish/"Commit & push" are the only actions, all calling `publish()`. **Caller precondition**: a component calling `useDocument` must not mount until both `collection` and `draftCollection`'s own `useLiveQuery(...).isReady` are true (`CollectionForm`'s `CollectionFormLive`/`GlobalForm`'s `GlobalFormLive` gate on exactly this) — `useAppForm` only snapshots `defaultValues` once, at first render, so mounting earlier freezes fields at empty/default values that never get replaced once real data arrives (this was a real, confirmed bug: a Base UI "uncontrolled → controlled" warning, and a document that looked empty despite having real remote data).
- **Every UI surface that shows "what does this document currently look like" has to consider the draft, not just the remote row — three real, previously-buggy instances of this, all fixed the same way.** (1) `CollectionTable`'s list view merges in `draftOnlyRows` (draft rows with no matching remote `id`) alongside real rows, so a document that's been drafted but never published still shows up (with a "Draft" status badge) instead of disappearing the moment you navigate away from it — remote data wins whenever a row exists in both places, so the list doesn't visually shift under someone editing the same document in another tab. Its per-row Delete button is row-aware for the same reason: a draft-only row's `id` isn't in the remote collection, so it deletes from `draftCollections[slug]` instead of calling `collection.delete()`. (2) `CollectionForm`'s `DocumentEditor` exposes a "Discard draft" (no remote row exists yet — deletes the local draft and navigates back to the list) / "Revert changes" (a remote row exists and the draft differs — resets the draft's `data` back to `remoteRow.data`, then navigates with `reloadDocument: true`, since `useAppForm` snapshots `defaultValues` once and won't otherwise re-render already-mounted fields) action, gated on `useDocument()`'s own `hasRemoteRow` — distinguishes "brand-new, nothing to revert to" from "published elsewhere, with local edits on top"; `isDirty` alone can't tell these apart, since it's `true` in both cases. (3) `Topbar`'s breadcrumb (`admin/views/topbar.tsx`'s `ItemBreadcrumbLive`) reads both `contentCollections[slug]` and `draftCollections[slug]`, preferring the draft's own `slug` — the *opposite* precedence from the list view, deliberately: you're actively typing in this document right now, so the breadcrumb should track what you're typing, not the last-published snapshot. Before this fix, all three only ever read the remote collection, which is what made local-first editing feel like it was silently forcing a publish — a document with no remote row yet was simply invisible/unreachable/stuck-on-"untitled" everywhere outside the open editor itself.

- **Migrations**: `www/drizzle.content.config.ts` (`schema` points at the consumer's own generated `db/schemas/content.ts`, `out: '.baseconfig/'`), applied via the `content:*` scripts (see the root `CLAUDE.md`'s "Commands"). See the root `CLAUDE.md`'s "Database" section for the binding itself.
- **A known, benign console warning**: `[cleanupQueryIfIdle] Invariant violation: refcount=1 but no listeners` — this comes from `@tanstack/query-db-collection` itself (`dist/esm/query.js`), not this app's code. In `eager` sync mode it increments its own internal `queryRefCounts` once at sync-start and never decrements it (`unloadSubset` is unset); listener attach/detach is driven separately, purely by subscriber count. Once a query's last listener unmounts and React Query's own idle GC later evicts that now-listener-less query, the refcount bookkeeping is already stale and the library logs this warning — a real decoupling inside the library, confirmed by reading its source, not something fixable from application code. It tends to fire whenever a whole admin section unmounts at once (e.g. a hard-reload sign-out).

#### The circular-import trap (read this before touching `registry.ts`/`db/collections.ts`)

`base/config/src/collections/registry.ts` is a **passive store** (`collectionsBySlug`/`globalsBySlug` start empty; `registerBaseConfig(collections, globals)` populates them) — it does **not** import `www/src/config/base.config.ts`. If it did: `base.config.ts` → its collection files → `defineCollection`/`defineGlobal` (`@baseconfig/core`) → `RelationshipField`/`NavMenuField` (composite fields) → `contentCollections` (`base/config/src/db/collections.ts`) → `registry.ts` → back to `base.config.ts`. That cycle is real and throws a hard TDZ crash under Bun's/Node's native ESM loader — Rollup/Vite happen to tolerate it, which is *why* it went unnoticed. `base.config.ts` (via `baseConfig()`) pushes into the registry; nothing pulls the app's config into the framework layer.

**A related, once-real bug for the same reason**: `www/src/api/index.ts` (the server-only `createHandler()` call) and `www/src/config/base.config.ts` (where every `Plugin` — e.g. `@baseconfig/plugin-form-builder`'s `formBuilderPlugin()` — actually registers its `endpointFactories`/`hooks`/`blocks` via `baseConfig()`) are two completely separate module graphs, each only loaded when its own route is first hit. `createHandler()` reads `collectEndpointFactories()`/`collectHooks()` **synchronously, once**, at `www/src/api/index.ts`'s own module-eval time — if nothing has forced `base.config.ts` to evaluate on the server first, that read sees an empty registry, and a plugin's own endpoint 404s forever for that isolate (confirmed with a real repro: a fresh dev server, first request straight at a plugin's endpoint, 404 in ~1ms — a pure routing miss, not a real 404). Fixed with one line: `www/src/api/index.ts` has a side-effect-only `import '@/config/base.config'` before its own `createHandler()` call, guaranteeing `baseConfig()` has already run. Safe to add — ES modules cache by specifier, so this doesn't double-run `baseConfig()`'s side effects even though the admin UI's own routes also import the same file.

#### SSR safety

`CollectionForm`/`GlobalForm` (`base/config/src/admin/*`) gate their entire subtree behind a `mounted` state flag before rendering `config.Fields` — this is why `MetaFields`/`RelationsField`/`RelationshipField`/`NavMenuField` (all of which call `useLiveQuery`) never need their own SSR guard. Don't add a *new* top-level admin surface that renders one of these composites without going through `CollectionForm`/`GlobalForm`'s existing mount gate.

#### The admin session guard: no route files, no consumer wiring at all

**Admin auth has zero route files of its own.** `login`/`create-account`/`forgot-password`/`reset-password` are reserved `$collection` values the *already-existing* `admin/$collection/$` catch-all resolves — the exact same one-dispatcher mechanism every real collection/global already goes through (`provider.tsx`'s `resolveRouteView`/`entry.tsx`'s `Entry`, see "Three admin namespaces" above), not a second routing system. `www/src/routes/` has exactly as many files as it would if this feature didn't exist. This replaced an earlier, more elaborate design (a separate `(auth)` pathless route group, four thin per-screen route files, a `guard.ts`-exported `adminLoader()`/`redirectIfAuthenticated()` pair a consumer wired into `loader:`) once a real technical blocker surfaced: TanStack Router loader `context` was never actually populated with `session` anywhere in the consumer app (no `beforeLoad` exists at all) — the loader-based guard type-checked but never received a real session at runtime. The fix was to stop trying to gate at the loader level and instead read session the same way `Topbar`'s own greeting already did: better-auth's client, not router context.

- **`useAdminSession()`** (`admin/functions/session-query.ts`) is the one shared session read every admin gate uses — `Topbar`, `ProviderView.Context`, `Dashboard`. **Not** a raw `authClient.useSession()` call per site: an earlier version of this had all three call `useSession()` independently (better-auth's own reactive client hook), which produced real, confirmed duplicate `/api/auth/get-session` traffic — each subscription re-fetched on its own. `useAdminSession()` instead wraps `createSessionQueryOptions()` (below) around `authClient.getSession()` (better-auth's *promise*-based client method, not `fetch`), so every caller shares one TanStack Query cache entry (`queryKey: ['base-config', 'session']`) — real deduplication. Returns `{data, isPending, hasSession}`; `hasSession` is the one boolean every caller branches on, and it's also `true` when `baseConfig()` was never given an `auth` client at all (nothing to gate against, same as this feature not existing). No manual cache invalidation on sign-in/sign-out — both already navigate with `reloadDocument: true`, which discards the whole client-side cache anyway.
- **Session gating lives in three places, all reading the same `useAdminSession()`**: **`Topbar`** (`admin/views/topbar.tsx`) always provides `AdminConfigContext` (plain app config, not chrome — `Entry`'s own `useAdminConfig()` call is unconditional, so this has to be true even when the chrome below is suppressed), then renders `TopbarChrome` only when `hasSession`, bare `children` otherwise (so the reserved-`$collection` auth screens render unwrapped) — plus a `useEffect` that redirects to `/` with a `?msg=` when a session exists but the role isn't `'admin'`, the one piece of the old loader-based guard that's still real, working gating, just moved to where a real session read is actually possible (a `loader` can't call a hook). **`provider.tsx`'s `resolveRouteView`** checks `hasSession` first: with no session, `slug` (i.e. `$collection`) resolves against the reserved auth-screen names instead of `collectionsBySlug`/`globalsBySlug`, defaulting to `'login'` for anything else; with a session, resolution is **100% unchanged** from before this feature existed. **`Dashboard`** (`admin/views/dashboard/component.tsx`) needs its own check too — `/admin` (bare index) is mounted by a *separate* route (`admin/index.tsx`) that never goes through the `$collection/$` catch-all at all, so `Topbar` hiding its own chrome doesn't stop `Dashboard` itself from still rendering underneath; `!hasSession` renders `LoginView` directly instead (no `$collection` segment exists at this bare path, so the fallback is unambiguous).
- **`entry.tsx`'s `Entry`** dispatches the four new `RouteViewState` modes (`context.tsx`) to `LoginView`/`CreateAccountView`/`ForgotPasswordView`/`ResetPasswordView` directly, with zero props — same file, same "just render whichever mode `useRouteView()` reports" job it already had for `list`/`edit`/`global`/`custom`/`not-found`.
- **`guard.ts`'s `requireAdminSession`/`adminLoader`/`redirectIfAuthenticated` still exist**, exported from `@baseconfig/core/admin` as a general-purpose *alternative* — a consumer whose own app genuinely does populate `context.session` (a real `beforeLoad`) could still use the separate-URL-redirect model these provide. `www` itself no longer calls any of them.

#### `Topbar`'s sign-out mutation (`base/config/src/admin/views/topbar.tsx`)

`Topbar` takes no `signOut`/`onSignOut` prop at all — it calls `getAuthClient()` and builds its own `useMutation` internally (inside `TopbarChrome`, only ever rendered once a session exists), deriving the button's `disabled`/label text from `isPending`. On success it navigates to `/admin/login` — still a real, working URL (the reserved-`$collection` dispatch above resolves it), just not a distinct route file anymore.

#### Admin auth screens, now fully self-contained with zero consumer props (`base/config/src/admin/views/auth/{auth-banner,login-view,create-account-view,forgot-password-view,reset-password-view}.tsx`)

Admin auth is entirely the library's own — there is no public-facing sign-in flow at all, and a consumer never renders any of these views directly (`entry.tsx` does, per the reserved-`$collection` dispatch above) or passes them props. Each owns its own zod schema and calls `authClient.*` (`getAuthClient()`) directly.

- **`LoginView`** — merges email and username sign-in into one `credentials` field (picks `signIn.email`/`signIn.username` based on whether the value looks like an email — "the same thing, different terminology"). Passkey sign-in and the 2FA challenge step are **feature-detected**, not configured: `authClient.signIn.passkey`/`authClient.twoFactor` are only present when the consumer's own `authClient.ts` actually registered those client plugins (`passkeyClient()`/`twoFactorClient()`) — a safe, real runtime check with no server round-trip. A successful `signIn.email`/`signIn.username` call whose result carries `twoFactorRedirect: true` swaps the form for an OTP-code step (`otpForm`, `authClient.twoFactor.verifyTotp`) rather than navigating away. Social sign-in **isn't** feature-detectable the same way (social providers are configured server-side with real secrets — no "list configured providers" client endpoint exists), so `icon`/`socialProviders` both default from `getAdminConfig()` (`admin/functions/config-registry.ts` — a plain module-level registry, not React context, set once by `baseConfig({config})`; a consumer states `config.socialProviders` once, app-wide, in `www/src/config/base.config.ts`, e.g. `['github', 'google']` to match what's actually configured in `auth.ts`) — both remain overridable props for a caller that wants something different, just never *required*.
- **`CreateAccountView`** — same boundary, `authClient.signUp.email` + `authClient.isUsernameAvailable` (debounced `onChangeAsync` validator on the username field). Same `getAdminConfig()`-defaulted `icon`/`socialProviders`.
- **`ForgotPasswordView`** — one `email` field, `authClient.requestPasswordReset({email, redirectTo: resetPasswordHref})`. Always shows the same "if that email exists…" confirmation regardless of whether the account actually exists — standard practice, never reveals account existence either way. `icon` defaults from `getAdminConfig()`.
- **`ResetPasswordView`** — the other half: reads its own `?token=` directly via `useSearch({strict: false})` (no `validateSearch` anywhere — there's no route file left to put one on, and a full zod-validated search schema was more ceremony than one optional string warranted), calls `authClient.resetPassword({newPassword, token})`. No token in the URL renders an error state instead of a form. `icon` defaults from `getAdminConfig()`.
- All four are typed against `BetterAuthAdminClient`'s widened structural type (`db/collections.ts`) — confirmed correct by real `tsc` errors against the actual `authClient` instance, not guessed: `authClient.requestPasswordReset`, not `forgetPassword` (better-auth's actual endpoint is `/request-password-reset`, confirmed by reading `api/routes/password.mjs`).
- `AuthBanner` (icon/title/description header every screen shares) takes `icon` as a plain URL prop rather than a hardcoded favicon path.

**`createSessionQueryOptions<TSession>(getSession: () => Promise<TSession>)`** (`admin/functions/session-query.ts`) still exists, still exported, but **`www` no longer calls it for the admin flow** — session reads there now go through `getAuthClient()?.useSession()` (above), not a `createServerFn()`+`queryOptions()` pair. It remains a real, usable option for a consumer that genuinely wants a server-fn-backed session query (e.g. one whose router really does populate `context.session` via a real `beforeLoad`).

#### Storage: a real R2-backed media library

File storage is real and server-backed — `MEDIA` (the R2 binding) has application code reading and writing it via `@baseconfig/core/api/storage-route`'s `createStorageRoute(bucket)` (`GET /list`, `POST /upload`, `DELETE /file`, `DELETE /folder`, all gated by an admin-only check on `session.user.role`). Uploaded files are served back at `{hostDomain}/<key>` through `www/src/routes/(web)/$.tsx`'s own `server.handlers.GET` (see the root `CLAUDE.md`'s "File-based routes" for why this route also renders public documents on the same path, and how the two coexist). The client side (`fields/storage-client.ts`) goes through a real `StorageApiClient` (Hono RPC, `createStorageApiClient`), never raw `fetch`.

- **Per-collection, per-document folder scheme.** Every collection/global gets its own folder automatically, named after its own `slug` — `createFieldsRenderer`/`createFlatFieldsRenderer` (`fields/renderer.tsx`) take a `uploadFolder` param, threaded down to every `upload` field's `renderField` call. Each field also gets the *document's own id* folded in, and an optional field-level `prefix` nested under that: `uploadPrefix = [uploadFolder, id, field.prefix].filter(Boolean).join('/')`.
- **The `meta` composite gets its own top-level folder** — SEO images land at `meta/<collectionSlug>/<id>/<filename>`.
- **The Storage admin page** (`admin/views/storage/component.tsx`, exporting `Storage`, dispatched via `ContextView.Storage`, mounted at `/admin/storage`) is a **real registered global**, `www/src/config/globals/storage.ts` — `defineGlobal({slug: 'storage', component: ContextView.Storage})`, using `GlobalConfig`'s `custom` capability. Folder-by-folder: real `Breadcrumb`/`BreadcrumbList`/etc., a grid of files, delete buttons on both (a deleted folder just deletes every R2 object under that prefix).
- **`StorageWidget`** (`admin/widgets/storage-widget.tsx`) is the `Upload` field's "choose existing, or drag-and-drop a new one" picker. Browses every file as **one flat list** (`GET /list?flat=true`).
