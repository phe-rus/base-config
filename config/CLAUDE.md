# CLAUDE.md — `base/config`

Internals of the `@base/config` engine — loads only when a session is working with files under `base/config/src/`. See the root `CLAUDE.md` for the boundary between this library and `www/src/config/` (the consumer), the three factories' basic shape, and the annotated directory tree.

#### Three admin namespaces: `RenderView`, `ContextView`, `ProviderView`

All three live under `admin/views/`. `RenderView` and `ContextView` are a plain function component with named sub-parts hung off it as properties (`export const X: XComponent = (...) => ...; X.Sub = (...) => ...`, typed via an intersection cast); `ContextView`/`ProviderView` are plainer — a bare object of named component references, since nothing ever renders `<ContextView>`/`<ProviderView>` directly, only their members:

- **`RenderView`** (`admin/views/render-view.tsx`) is markup-level reuse: the page-container chrome every top-level admin view shares. `RenderView` itself is the outer `<article className='container flex flex-col w-full md:max-w-4xl mx-auto gap-5 py-5'>`; `.Header`, `.NotFound`, `.List` (a titled grid of link cards), `.Breadcrumb`, `.FolderCard`/`.FileCard` (Storage's grid rows) are the named sub-parts.
- **`ContextView`** (`admin/views/context-view.tsx`) is route-dispatch-level grouping: `{Dashboard, Entry, Storage}`. **`ContextView.X` must never be written directly as a route's `component:`** — every consumer route destructures to a local const first (`const { Entry } = ContextView` then `component: Entry`).
- **`ProviderView`** (`admin/views/provider.tsx`) is `{Context}` — one member, `ProviderView.Context`, the component a consumer wraps the `$collection` layout route's `Outlet` in. It resolves `RouteViewState` once per navigation and provides it via `useRouteView()`. Unlike `ContextView` members, `<ProviderView.Context>` is used as plain JSX inside a route file's own component body, not as a route's `component:` value.

#### The three factories (`base/config/src/define.ts`)

- **`defineCollection({slug, label?, color?, path?, auth?, columns?, filterKey?, admin?, tabs})`** → a full `CollectionConfig` (`schema`, `defaultValues`, `Fields` all derived automatically from `tabs`). `label` is optional (derived via `labelFromSlug(slug)` if omitted). `path` sets the collection's public URL prefix. `auth: true` marks the real, server-backed `users` collection — every other collection is real D1-backed content (see "Content persistence" below). `columns`/`filterKey` control `CollectionTable`'s columns. `admin.useAsTitle` names a real field to display as a document's "title" for collections without one (`users` uses `name`).
- **`defineGlobal({slug, label?, fields})`** → a full `GlobalConfig`, same derivation, minus tabs. **Or** `defineGlobal({slug, label?, component})` → a `custom: true` global whose `Fields` is `component` directly, with no schema/document/`GlobalForm` wrapper — `admin/views/provider.tsx`'s `resolveRouteView` checks the generic `config.custom` flag and resolves it to `mode: 'custom'`, which `ContextView.Entry` renders as the whole page. For a global that isn't really a document to edit — e.g. Storage.
- **`baseConfig({queryClient, auth?, config, collections, globals, ...})`** → identity function with several side effects: registers every `collections`/`globals` entry with `base/config/src/collections/registry.ts`; registers `queryClient`/`contentClient`/`storageClient` unconditionally via `registerContentDataSource()`/`registerStorageDataSource()` (every consumer needs real content persistence, not just `auth`-enabled ones); if `auth` is passed, calls `registerUsersDataSource({queryClient, authClient: auth})`. Returns the same config either way.

#### Field types (`base/config/src/fields/types.ts`)

Primitives (dispatched generically to a matching `@base/ui/forms` control — see `base/ui/CLAUDE.md` for the full, much larger current vocabulary): `text`, `textarea`, `richtext`, `checkbox`, `switch`, `date`, `keywords`, `upload`, `select`, `radio`, plus the newer leaf types `email`/`number`/`password`/`confirmPassword`/`hidden`/`code`/`json`/`slug`/`point` (not yet all wired into this union — see `base/ui/CLAUDE.md`'s field-type table for exactly which `@base/ui/forms` components exist vs. which have a corresponding `FieldConfig` variant here; adding the `FieldConfig` union entry + resolver wiring for one is a small, mechanical follow-on, not yet done for most of them). `array` recurses (its own `fields` describe one item's shape; nested array item paths compose via `${path}.${field.name}`).

Composites (each dispatched directly to an app-supplied component via `define.ts`'s resolver maps, not through the generic primitive switch): `blocks` (page-content blocks), `relationship` (single/multi document reference), `relations` (the "related posts" manual-or-keyword-filter composite), `meta` (SEO title/description/image/keywords bundle), `menu` (nav menus). **Layout/grouping field types Payload has that this doesn't yet** (`group`, `row`, `collapsible`, `tabs`-as-a-field, `join`) would need real schema-nesting support added to this union first — a plain `base/ui` UI component alone wouldn't be enough, since `FieldConfig` today has no concept of "a field that contains other fields except `array`."

**Tabs are a UI grouping only, not a schema-nesting concept.** A field's `name` is resolved relative to its own tab via `withTabPrefix` (`fields/schema.ts`): `tab: 'post'` + `name: 'content'` → real path `post.content`; the prefix is *skipped* when the field's name already equals its tab id.

**`defaultValues` is never hand-written.** `deriveDefaultValues` (`fields/schema.ts`) walks a collection/global's fields and only sets a value when a field explicitly has `defaultValue`, or is one of the container types that default to an empty container (`array`/`blocks`/`relations`/`menu` → `[]`, `meta` → `{title: '', description: ''}`).

#### Relationships (`base/config/src/collections/fields/relationship-field.tsx`)

A selected relationship stores `{id, slug, title}` (`RelationshipValue`), not a bare id. The picker itself queries **every real collection via a fixed number of `useLiveQuery` calls** (`pages`/`posts`/`policies`, one each) — adding a fourth collection means adding one more explicit `useLiveQuery` line in `useRelationshipOptions`. `hasMany` switches between `RelationshipFieldSingle` (plain combobox) and `RelationshipFieldMulti` (chips).

#### Nav menus (`menu` field type, `base/config/src/collections/fields/nav-menu-field.tsx`)

Used by both `footer` and `topbar`. Every item is a **link by default**: `mode: 'internal'` (a `RelationshipField` reference — picking one auto-syncs `to` via `collectionPath(collectionsBySlug[value.collection], value.slug)`) or `mode: 'custom'` (hand-typed `to`), plus `appearance` (a real shadcn `Button` variant) and `openInNewTab`. Checking **"Mega menu"** drops the link fields and shows a **"Category"** toggle. There is no public-facing render of any of this yet — this is authoring-side only.

#### The global keyword pool

`registerKeyword`/`useGlobalKeywordSuggestions` (`base/config/src/db/collections.ts`) are **not** their own collection — the shared, site-wide keyword pool *is* the `keywords` global's own document inside `globalsCollection`. Typing a new keyword anywhere a `KeywordsInput` is used both suggests from and writes into that same document, and it's directly editable as a real list at `/admin/keywords`.

#### The real, server-backed `users` collection (`auth: true`)

`users` (`www/src/config/collections/users.ts`) is one of two persistence models a collection can have — real accounts through better-auth's `admin()` plugin via `authClient.admin.*`, as opposed to every other collection's real D1-backed content (see "Content persistence" below; earlier states of this doc described every non-`users` collection as `localStorage`-only — that's no longer true). Everything below lives in `base/config/src/db/collections.ts` unless noted:

- **`RealUserRow`** is a closed type listing only the fields this library cares about; `toUserDocumentRow(user)` destructures the known fields out and spreads `...rest` into `data` regardless, so an app-added field flows through with zero library changes.
- **Creation bypasses `collection.insert()` entirely** — `createRealUser(collection, input)` calls `authClient.admin.createUser(input)` directly and writes the *confirmed* row via `collection.utils.writeInsert(...)`, because a client-generated temp id can never match the server-assigned real id. `AuthWidget` (`admin/widgets/auth-widget.tsx`) is `CollectionTable`'s create-button replacement for `auth: true` collections.
- **`onUpdate` sends a real diff, not the whole document** — `Object.is`-compares `mutation.original.data`/`mutation.modified.data` per key (always excluding `title`/`slug`/`password`), skips the API call entirely if nothing changed.
- **Manual save only, same as every other collection now** — `useDocument()` has no auto-save at all (local-first: editing a field only ever touches form state; a real write happens only on an explicit Save/Publish click, see `db/use-document.ts`'s own doc comment). `auth: true` collections keep their one "Commit & push" button; every other collection gets Save/Publish/Unpublish.
- **Users aren't a relatable content type** — `RelationshipField`'s `useRelationshipOptions` deliberately excludes `'users'`.
- **`unwrap<T>({data, error})`** throws `error` directly if it's already an `Error`, else extracts `.message` if present, else `JSON.stringify`s it.
- If you're chasing a "list users" request that never resolves, check the installed `@better-auth/drizzle-adapter` version first — rc.1's unfiltered `findMany` had a real upstream bug fixed in rc.2.

#### Content persistence: real D1, via Drizzle (not `localStorage`)

Every collection/global except `users` is now real, server-backed content — a D1-backed database, `BASECONFIG` (see the root `CLAUDE.md`'s "Database" section), queried through the library's own Drizzle layer, not `localStorage`. This is a real reversal of an earlier state of this doc (and, mid-implementation this session, a real reversal from raw SQL to Drizzle) — if older notes describe `contentCollections`/`globalsCollection` as client-only `localStorageCollectionOptions`, that's stale.

- **Schema, queries, and the Hono route all live in the library** (`base/config/src/db/{content-schema,content-queries,content-route}.ts`), not in `www` — a consumer's own footprint is exactly one line: `www/db/content-db.ts` is `export const contentdb = drizzle(env.BASECONFIG, {logger: false, relations: contentRelations})`, nothing else. `contentRelations` itself is exported from the schema file (`content-schema.ts`), not built by the consumer.
- **`content-schema.ts`**: `documents` is one shared table parameterized by `collection` (not one table per slug), so adding a new collection to `www/src/config/` never needs a migration — columns are `id`, `collection`, `title`, `slug`, `status` (`'draft' | 'published'`), `data` (JSON, everything beyond the fixed columns), `createdAt`, `updatedAt`. `globals` is one row per global slug — no `id`/`title`/`status`, just `slug`, `data`, `updatedAt`. A consumer regenerates its own copy via `bun x base --output=<path>` (the library's own CLI, `base/config/src/cli.ts`) — never hand-copies this file.
- **`content-queries.ts`**: `listDocuments`/`getDocument`/`createDocument`/`updateDocument`/`deleteDocument`/`listGlobals`/`getGlobal`/`upsertGlobal`, each taking a `ContentDatabase` (= `DrizzleD1Database`, structural — a consumer only ever hands this package `drizzle(env.BASECONFIG, ...)`, nothing more) as the first param. `updateDocument`/`upsertGlobal` only write what changed — fixed columns get a direct `.set()` only when provided, and the caller's own `fields`/diff object gets *merged* into the existing `data` blob (`{...existing.data, ...fields}`), never a whole-document replace. `listDocuments` supports a narrow `where`/`limit`/`page` (top-level columns only — `status`/`slug` via `equals` — not arbitrary JSON-field querying) and returns a Payload-style paginated envelope (`{docs, totalDocs, limit, page, totalPages, hasNextPage, hasPrevPage}`).
- **`content-route.ts`**: `createContentRoute(db)` — a Hono factory (not a pre-built app) a consumer calls and mounts themselves, matching `createStorageRoute(bucket)`'s own shape. Mounted at the API's own root by `createBaseConfigRoute()` — a collection's real REST address is `/api/<collection>`, a global's is `/api/globals/<slug>`, matching Payload's own REST shape. Real `@hono/zod-validator` schemas gate `POST`/`PATCH` bodies and the list route's query params. Reads are public (drafts filtered out for non-admins); writes are admin-only, same `session.user.role === 'admin'` gate as storage. `/globals` is registered before the `/:collection` wildcard in the route's own chain — Hono resolves an ambiguous match by registration order, not static-vs-dynamic priority, confirmed empirically.
- **Client side** (`base/config/src/db/collections.ts`): `contentCollections`/`globalsCollection` are real `queryCollectionOptions` (tanstack-db) backed by a real `ContentApiClient` (Payload-Local-API-named methods — `find`/`findByID`/`create`/`update`/`delete`/`findGlobal`/`updateGlobal` — built via `createContentApiClient(route.api)` from the consumer's own Hono RPC client, never raw `fetch`), with the same lazy, mutation-triggered-refetch policy the real `users` collection already used (`staleTime: Infinity`, explicit `.refetch()` after a mutation resolves — not a time-based re-fetch). `registerContentDataSource({queryClient, client})` is called unconditionally inside `baseConfig()`. `globalsCollection` specifically needed a `createLazyCollection()` Proxy helper — it used to be created eagerly at module-load time (safe when it was pure `localStorage`), but a query-backed version needs `registerContentDataSource()` to have already run first, which isn't guaranteed at that point — the Proxy defers actual creation to first property access, by which point app bootstrap has completed. A ready-to-import `base` object (`db/content-client.ts`, exported from `@base/config`'s barrel) wraps the same client as TanStack Query `queryOptions()`/`mutationOptions()` — `useQuery(base.find({collection: 'posts'}))`, `useMutation(base.createMutation('posts'))` — for application code outside the admin engine's own collections.
- **Migrations**: `www/drizzle.content.config.ts` (`schema` points at the consumer's own generated `db/schemas/content.ts`, `out: '.baseconfig/'`), applied via the `content:*` scripts (see the root `CLAUDE.md`'s "Commands"). See the root `CLAUDE.md`'s "Database" section for the binding itself.

#### The circular-import trap (read this before touching `registry.ts`/`db/collections.ts`)

`base/config/src/collections/registry.ts` is a **passive store** (`collectionsBySlug`/`globalsBySlug` start empty; `registerBaseConfig(collections, globals)` populates them) — it does **not** import `www/src/config/base.config.ts`. If it did: `base.config.ts` → its collection files → `defineCollection`/`defineGlobal` (`@base/config`) → `RelationshipField`/`NavMenuField` (composite fields) → `contentCollections` (`base/config/src/db/collections.ts`) → `registry.ts` → back to `base.config.ts`. That cycle is real and throws a hard TDZ crash under Bun's/Node's native ESM loader — Rollup/Vite happen to tolerate it, which is *why* it went unnoticed. `base.config.ts` (via `baseConfig()`) pushes into the registry; nothing pulls the app's config into the framework layer.

#### SSR safety

`CollectionForm`/`GlobalForm` (`base/config/src/admin/*`) gate their entire subtree behind a `mounted` state flag before rendering `config.Fields` — this is why `MetaFields`/`RelationsField`/`RelationshipField`/`NavMenuField` (all of which call `useLiveQuery`) never need their own SSR guard. Don't add a *new* top-level admin surface that renders one of these composites without going through `CollectionForm`/`GlobalForm`'s existing mount gate.

#### The admin session guard (`base/config/src/admin/functions/guard.ts`)

`requireAdminSession(session, {loginTo, unauthorizedTo, role?, unauthorizedMessage?})` is the mechanism behind an `(admin)`-style route's `loader`: no session → `redirect({to: loginTo})`; session but wrong `role` (defaults to `'admin'`) → `redirect({to: unauthorizedTo, search: {msg: unauthorizedMessage}})`; otherwise returns `{session}`. Session is typed structurally (`{user: {role?: string | null}}`), same trade-off as `Topbar`'s `sessions` prop — this package has no dependency on any particular auth library.

#### `Topbar`'s sign-out mutation (`base/config/src/admin/views/topbar.tsx`)

`Topbar` takes no `signOut`/`onSignOut` prop at all — it calls `getAuthClient()` and builds its own `useMutation` internally, deriving the button's `disabled`/label text from `isPending`. The sign-out button only renders at all if `authClient` is truthy.

#### Admin auth screens (`base/config/src/admin/views/{auth-banner,login-view,create-account-view}.tsx`)

`LoginView`/`CreateAccountView` (exported from `@base/config/admin`) are the real sign-in/sign-up screens — moved into the library, replacing what used to be `www`-only page components. A consumer's own better-auth *server* config and `createServerFn()` mutation layer stay entirely the consumer's own — these components only ever receive already-built `schema`/`defaultValues`/`onSubmit` (and, for `CreateAccountView`, `onCheckUsername`) as props, the same boundary `Topbar`'s sign-out button and the real `users` collection already draw around better-auth. `schema` props are typed loosely (`z.ZodTypeAny`), matching `useDocument`'s own established convention, rather than fighting zod's generic variance for a strict type. Both auto-`form.reset()` after their `onSubmit` resolves (success or failure) — matches the original `www`-only pages' behavior. `AuthBanner` (icon/title/description header both share) takes `icon` as a plain URL prop (e.g. a consumer's own `config.adminIcon`) rather than a hardcoded favicon path. See the root `CLAUDE.md`'s "File-based routes" section for how `www`'s own `(auth)/auth/{index,create-account}.tsx` route files wire these up.

#### Storage: a real R2-backed media library

File storage is real and server-backed — `MEDIA` (the R2 binding) has application code reading and writing it via `@base/config/api/storage-route`'s `createStorageRoute(bucket)` (`GET /list`, `POST /upload`, `DELETE /file`, `DELETE /folder`, all gated by an admin-only check on `session.user.role`). Uploaded files are served back at `{hostDomain}/<key>` through `www/src/routes/$.ts`, a root-level splat **server route** (`server: {handlers: {GET}}`, not a page component) — the lowest-priority route in the app. The client side (`fields/storage-client.ts`) goes through a real `StorageApiClient` (Hono RPC, `createStorageApiClient`), never raw `fetch`.

- **Per-collection, per-document folder scheme.** Every collection/global gets its own folder automatically, named after its own `slug` — `createFieldsRenderer`/`createFlatFieldsRenderer` (`fields/renderer.tsx`) take a `uploadFolder` param, threaded down to every `upload` field's `renderField` call. Each field also gets the *document's own id* folded in, and an optional field-level `prefix` nested under that: `uploadPrefix = [uploadFolder, id, field.prefix].filter(Boolean).join('/')`.
- **The `meta` composite gets its own top-level folder** — SEO images land at `meta/<collectionSlug>/<id>/<filename>`.
- **The Storage admin page** (`admin/views/storage/component.tsx`, exporting `Storage`, dispatched via `ContextView.Storage`, mounted at `/admin/storage`) is a **real registered global**, `www/src/config/globals/storage.ts` — `defineGlobal({slug: 'storage', component: ContextView.Storage})`, using `GlobalConfig`'s `custom` capability. Folder-by-folder: real `Breadcrumb`/`BreadcrumbList`/etc., a grid of files, delete buttons on both (a deleted folder just deletes every R2 object under that prefix).
- **`StorageWidget`** (`admin/widgets/storage-widget.tsx`) is the `Upload` field's "choose existing, or drag-and-drop a new one" picker. Browses every file as **one flat list** (`GET /list?flat=true`).
